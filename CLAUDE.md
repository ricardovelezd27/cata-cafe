# Cata Café — Project Guide for Claude

## What This Project Is

**Cata Café** is a professional coffee cupping evaluation platform for specialty coffee experts (catadores). It implements the SCA CVA (Specialty Coffee Association — Coffee Value Assessment) methodology, enabling structured sensory evaluations across three formats: Descriptive, Affective, and Combined. Users create cupping sessions, evaluate individual coffee samples cup-by-cup, and generate scored reports and PDF certificates.

Target users: coffee professionals conducting blind tastings in a lab or production environment.
Default language: Spanish (`es`). Secondary: English (`en`).

## Critical Warnings

### Next.js 16 — Breaking Changes
This project runs **Next.js 16.4.6**, which contains breaking API changes from 14/15. Before writing any Next.js-specific code (routing, layouts, middleware, server actions, caching), read the relevant guide in `node_modules/next/dist/docs/`. Do not assume any Next.js behavior from training data.

### Next.js 16 — Middleware File Name Is `proxy.ts` (NOT `middleware.ts`)
**Confirmed via build error:** Next.js 16 uses `proxy.ts` at the project root as the middleware file. The function must be exported as `proxy` (not `middleware`). If you create `middleware.ts`, the build will error: *"Both middleware file './middleware.ts' and proxy file './proxy.ts' are detected. Please use './proxy.ts' only."* The build output shows `ƒ Proxy (Middleware)` when correctly configured.

### Async Page Params
Page props always use `params: Promise<{ locale: string; id?: string }>`. Always `await params` before destructuring:
```ts
export default async function Page({ params }: { params: Promise<{ locale: string; id: string }> }) {
  const { locale, id } = await params;
  setRequestLocale(locale);
  // ...
}
```

### Prisma Client Location
The generated Prisma client lives at `app/generated/prisma/` — **not** `@prisma/client`. Always import from the generated path:
```ts
import { PrismaClient } from "@/app/generated/prisma";
```
Never edit files in `app/generated/prisma/`. After any `schema.prisma` change, run:
```bash
npx prisma migrate dev
npx prisma generate
```

### Tailwind CSS 4
This project uses **Tailwind CSS v4** (PostCSS-based). There is no `tailwind.config.js` class safelist — Tailwind scans source files for class names. Do not generate class names dynamically via string concatenation.

## Architecture & Conventions

### Locale-First Routing
Every app route lives under `[locale]`. Every page component must:
1. Call `setRequestLocale(locale)` as the first line (enables static rendering)
2. Export `generateStaticParams()` returning `[{ locale: "es" }, { locale: "en" }]` — **but ONLY on routes whose sole dynamic segment is `[locale]`**.

**EXCEPTION — authed pages with an extra dynamic segment (`[id]`, `[token]`):** do NOT export `generateStaticParams` (not even returning `[]`). With it present, production attempts on-demand static generation and the `cookies()` call inside the Supabase client crashes the route with a 500 — while dev renders dynamically and hides the bug. Instead export `export const dynamic = "force-dynamic";` (see `app/[locale]/join/[token]/page.tsx`, `app/[locale]/app/groups/[id]/page.tsx`). This caused a real production outage on 2026-07-21 (groups/[id] and coffees/[id] returned 500 for every user).

### Server Components by Default
Pages and layouts are async RSC. Add `"use client"` only to components that use browser APIs, event handlers, or React state. Client components in `components/cupping/` receive data as props.

### Mutations via Server Actions
All writes go through `app/actions/`. Call `revalidatePath()` after mutations to invalidate the Next.js cache. Never write to the database from client components directly.

### Server Action Contract (2026-09 error-handling foundation)
- A thrown error inside a server action reaches the browser as an **opaque digest** in production. So every action that a client component calls **interactively** (button, toggle, dialog, form) must return `ActionResult<T>` (`lib/actionResult.ts`: `{ ok: true, data } | { ok: false, error: ActionErrorCode }`) by wrapping its body in `run("actionName", async () => { … }, { userId, sessionId })` from `lib/safeAction.ts`. `run()` lets `redirect()`/`notFound()` through (`unstable_rethrow`), maps the known thrown codes (`not_authenticated`, `not_found_or_forbidden`, `session_closed`, `token_*`, `coffee_not_usable`, `invalid_input`) and Prisma `P2002 → conflict`, `P2025 → not_found`, `P2003 → invalid_reference`, and logs everything else as `unknown`. Keep throwing `Error("<code>")` INSIDE the body — that is the mechanism, not a smell.
- Actions only called from server pages, or already wrapped by `ConfirmDialog`, may keep throwing. Reference conversion: `completeOnboarding` in `app/actions/profile.ts`.
- **Client side**: never `startTransition(async () => { await action() })` bare. Use `const feedback = useActionFeedback()` (`components/ui/Toast.tsx`, provider mounted in `app/[locale]/layout.tsx`) and `feedback.run(action(...), onOk)` — it toasts the localized copy for `errors.codes.<code>` on failure. Actions that still throw are wrapped in try/catch → `feedback.notifyError("unknown")`. Plain `<form action>` pages use React 19 `useActionState` with a `(prev, formData)` action (see `components/join/*Form.tsx`).
- Copy for every `ActionErrorCode` lives in `messages/*.json` under `errors.codes`; adding a code means adding both translations.
- **S8-14**: group roster/post actions and the insight actions (`runInsight`, `runPivot`, `saveInsight`, `deleteSavedInsight`, `runBenchmark`, `runOriginContext`, …) follow this contract. `group_full`, `invalid_email` and `offline` were added (`offline` is raised client-side by `feedback.run` when `navigator.onLine === false`). Background auto-runs (debounced explorer/pivot) toast only `isAccessError` codes. A server page never calls an action for a read: `lib/analytics/savedInsights.ts` is the read helper.
- **Digest + chat quota (S8-14)**: the monthly digest claims its `digest_runs` period as `running` BEFORE sending and releases it when nothing was sent (`lib/digestClaim.ts`); the insights-chat question slot is reserved atomically before the model loop and released when no model call succeeded (`lib/ai/chatQuota.ts`). Group email links never carry the recipient address. The founding cohort size is `FOUNDING_SEATS` (`lib/landing/founding.ts`), copy only, never enforced.

### Validation
- `lib/validate.ts` (`str`, `int`, `oneOf`, `isoDate`, `list`, `email`, `cupFlags`, `cupDefectTypes` (never throws: exactly `cups` entries, anything not a defect id becomes `null`)) — no zod. Every client-posted string/number/enum/date/array goes through one of these before Prisma; they throw `invalid_input` (mapped by `run()`), or the caller translates to its own code (the session wizard's `validateSessionMeta` → `session.newForm.errors.*`).
- **Scoring inputs are never taken from the client**: `upsertEvaluation` and `syncEvaluation` read `cupsPerSample` and `format` from the session row (`requireSample*` return them) and derive the JSON column via `moduleKeyForFormat`; `computeEvaluationDerived` clamps the cup arrays with `cupFlags`. The `cupsPerSample` / `moduleKey` fields in those inputs are kept for API compatibility and ignored.

### Logging
- `lib/log.ts` (`logError` / `logWarn` / `logInfo`) writes one JSON line per event so Vercel Logs can be searched by `digest`, `action`, `sessionId`. `run()` logs unknown action failures; `instrumentation.ts` logs render/route failures with the same shape.
- **Log**: action name, error code, digest, ids (userId/sessionId/coffeeId/groupId), the route template, locale, and `message` only for `unknown`. **Never log**: request headers/cookies, concrete `/join/*` or `/auth/*` paths (tokens — use `redactPath`), emails, display names, form bodies, evaluation payloads, AI prompts.

### Auto-Save in CupClient
`CupClient` debounces evaluation saves at 800ms. Do not add additional `revalidatePath` calls that would trigger a full re-render on every keystroke — the debounce exists to batch writes.

### Evaluation Data Shape
`descriptiveData`, `affectiveData`, and `combinedData` on the `Evaluation` model are stored as JSON (`Record<string, unknown>`). Do not flatten these into new columns — the flexible JSON structure is intentional to support dynamic attribute sets.
**Per-cup defect type (S10 WP1b, `TODO(kim-validar:A3)`):** the module JSON key `tazas_defecto_tipo` holds one entry per cup (length = the session's `cupsPerSample`), each a `SENSORY_DEFECTS` id (`moldy | phenolic | potato`) or `null`. It is JSON ON PURPOSE (no column, no migration). `computeEvaluationDerived` (the one derivation of the live save and the offline replay) is the only place that decides what counts: key ABSENT = legacy blob, stored exactly as posted (a flagged cup with no type still counts and reads "sin especificar"); key PRESENT = a flagged cup is ALWAYS defective, typed or not (an untyped one counts as "sin especificar"; a deduction already recorded never disappears because its type is missing, decision doc 5.3), a type on an unflagged cup is cleared, with 2+ cups a defective cup is forced non-uniform, and `defecto_tipo` / `Evaluation.defectTypes` are DERIVED from it (distinct NON-null types of the defective cups, in `SENSORY_DEFECTS` order). "A type is mandatory" lives in the FORM only: marking a NEW cup defective needs a type, a legacy flagged cup keeps its mark and the chip "Falta el tipo de defecto" (tappable to choose one), nothing but deliberately unmarking it removes it, and submit is never blocked by a missing type. `lib/cupDefects.ts` holds the pure readers/helpers: `defectTally(data, cups)` (the one reader of "which cups were defective and of which type"; reusable for the coffee lifetime tally), the form's `applyDefectChoice` / `applyNonUniformToggle` (the non-uniform row never removes a defect: on a defective cup the tap opens the type chooser and the helper changes nothing), and `formCupState` (seeds a legacy draft's flagged cups from its single legacy type; cups with no single type stay flagged and untyped). `pinReferenceAffective` clears the key too.

### Auth Pattern
- `requireUser()` helper in every server action — throws/redirects if unauthenticated. That is AUTHENTICATION only.
- **AUTHORIZATION** for session-scoped actions goes through `lib/sessionAuth.ts`: `requireSessionOwner`/`requireSessionMember` (by session id) and `requireSampleOwner`/`requireSampleMember` (by sample id — also returns the sample's real `sessionId`; never trust a client-supplied sessionId next to a sampleId). Every new session/sample mutation MUST call one of these — Prisma connects as postgres and bypasses RLS, so these TS checks are the real gate.
- Protected layout at `app/[locale]/app/layout.tsx` redirects to login
- Session stored in cookies via `@supabase/ssr`; refreshed by `proxy.ts` middleware on every request
- Sign-in is passwordless and has three entry points: the **email link** (opens `/auth/confirm`, a button completes it), the **6-digit code** typed on the login screen (`verifyEmailCode`), and **Google**; walk-up guests are anonymous Supabase users. There are no passwords in this system. (Details in "Sign-in deep links, code entry and locale" below.)
- `signInWithMagicLink(formData, next?)` threads `next` into `emailRedirectTo` → `/auth/callback?next=...` → callback at `app/auth/callback/route.ts` reads `?next=` and redirects there after auth. Used for invite links that require auth before joining.
- Owner vs participant rule (product-wide): the creator of an asset (session, coffee, group) has full create/edit/delete; participants/members only take part (evaluate, read the feed, leave a group).
- **Registered-only actions (S8-03)**: anything that creates an asset, shares, invites or sends email calls `requireRegisteredUser()` (`lib/auth.ts`, `isRegisteredUser` in `lib/guestScope.ts`) — never bare `requireUser()` — because `proxy.ts` gates pages, not server-action POSTs. Every export of `coffees.ts` and `groups.ts`, plus `createSession`/`createExpressSession`/`createGroupSession`/`duplicateSession`/`createInviteToken`, is pinned by `tests/registeredOnlyActions.test.ts`. Guests keep `requireUser()` for join, evaluate, submit, waiting room, offline replay and claim.
- **Outbound email is budgeted (S8-03)**: reserve BEFORE sending with `reserveEmailBudget` (`lib/emailBudget.ts`; numbers in `lib/emailLimits.ts`, ledger `outbound_email_events` keyed by HMACs from `lib/emailKeys.ts`, never a raw address or IP). Sign-in links go through `sendMagicLink` (`lib/magicLink.ts`, origin via `pickTrustedOrigin`); group mail goes through `deliverGroupMail` (`lib/groupEmail.ts`, per-recipient `group_email_deliveries` ledger, bounded retry, results labelled by name or `maskEmail`). A refusal is the typed code `rate_limited`; if the DB write already succeeded the action returns ok with `emailBlocked: "rate_limited"`. Logs carry ids and codes only, never an address or a provider response body. ### Offline-First Pattern
- The offline draft store (`lib/offline/store.ts`) wraps **localforage/IndexedDB** and is **client-only**. It is accessed through a lazy `instance()` getter that returns `null` during SSR, so an accidental server import degrades to a no-op instead of crashing. **Never import `lib/offline/store` from a Server Component or server action.**
- Drafts are keyed by session + user (`cata_session_<sessionId>_user_<userId>`). Connectivity is tracked by `hooks/useConnectivity.ts`; `hooks/useOfflineSync.ts` drains the queue on reconnect.
- Reconnect replay goes through `app/actions/offline.ts`, which keeps the **same authorization as the live path** — Prisma scoped by `cupperId`, never a raw Supabase select, so RLS/ownership rules hold. Conflict rules: no row → create; existing draft → local wins; already submitted → `conflict` unless `force`. `isDraft`/`submittedAt` are never mutated by replay.
- **Write ordering (S8-18)**: evaluation writes may carry an optional `clientTs` (ms epoch of the edit); `lib/evaluationWrite.ts` `writeEvaluationOrdered` (shared by `upsertEvaluation` and the replay core) ignores a strictly older one atomically against `Evaluation.lastClientWriteAt` (rule in `lib/offline/clientWrite.ts`). Absent/invalid `clientTs` = legacy upsert. The column is ordering metadata only: never read it from scoring, the trigger or `AggregateScore`.
- `lib/evaluation.ts` (`computeEvaluationDerived`) computes derived scores for both the live and offline paths so a replayed draft scores identically.
- **Draft status machine (S8-09)**: `lib/offline/status.ts` (pure, tested) owns the transitions: `pending | synced | conflict | failed | closed_unsent | orphaned`. Replay actions (`replayEvaluation/Physical/Extrinsic`) RETURN `synced | conflict | closed | pending | gone | rejected` and never throw for those; `syncEvaluation` keeps its legacy contract but does NOT keep old bundles working across a deploy: Next 16 recomputes server-action ids per build, so a tab left open across a deploy gets "Server Action not found" and shows "pending" until reloaded (drafts stay safe on the device; S8-23 C-06). The hook applies a result only via `applyReplayOutcome(..., { ifUpdatedAt })` so an edit made mid-flight stays `pending`; 5 failed runs park a module as `failed` (manual retry revives it); `closed_unsent`/`orphaned`/`failed` never block the final submit and are listed in the "Notas sin sincronizar" panel (read, copy, confirmed discard, nothing auto-deleted). One module-level lock in `useOfflineSync` means two hook instances never replay at once; replay also runs on resume (`hooks/useResume.ts`). Conflicts are rebuilt from the blobs, never kept only in React state.
- **Sign-out and claim guards (S8-09)**: `UnsyncedGuardProvider` (app layout) exposes `confirmLeave("signOut" | "claim")`; `SignOutButton` and `useGuestClaim` call it. The claim stores the anonymous id in localStorage `cata_claim_anon` when it starts and `ClaimCard` writes the completion marker `cata_claim_done` once `confirmGuestClaim` returns ok (`lib/offline/claimMarker.ts`); the next app mount under that confirming, non-anonymous id runs `rekeyUserBlobs`. `purgeCachesOnUserChange` drops the page/RSC caches when the signed-in id differs from `getLastUser()`.
- `ActionErrorCode` includes the client-only `offline`; `feedback.run` maps a dropped request to it (`isNetworkFailure`). TODO(C1): send-to-owner of `closed_unsent` notes; TODO(E5): queued session creation offline.

## Scoring System

The SCA CVA scoring formula is implemented in `lib/scoring.ts`. **Do not reimplement it.**

### The deduction rule (S10 WP1a — one formula, three scopes)
The score that existed before S8 was right in principle and had bugs; S8-04 removed the deductions below five cups instead of fixing them. This goes back to the principle (flagged cups cost points at ANY cup count, and everyone's cups share the deduction) and fixes three bugs: (1) a cupper with fewer than five cups saw no deduction in their stored score; (2) with fewer than five pooled cups the stored group score amplified the deduction (1 defective cup of 2 cost 20); (3) a defective cup was counted twice in the group (8 points for 1 of 5; the CVA and the individual score say 6). It is not a new scoring system. Spec: `docs/product/cata-descentralizada-puntaje.md`.

```
S                 = 0.65625 × Σhᵢ + 52.75 − uniformityPenalty − defectPenalty        (rounded to 0.25, clamped 0..100)
factor            = 5 ÷ max(5, cups)
uniformityPenalty = 2 × nonUniform × factor
defectPenalty     = 4 × defective  × factor
```
- `hᵢ` — final value (1–9) for each of 8 affective attributes
- `nonUniform` / `defective` — flagged cups, counted independently from the two arrays and clamped to the evaluation's cups (`evaluationCupCounts`). A defective cup is ALSO flagged non-uniform by `AffectiveForm`/`CombinedForm`, so it sits in both arrays and costs 4 + 2 = 6. Never more than 6 per flagged cup.
- Non-uniformity exists only for an evaluation with 2 or more cups: with 1 cup it is neither counted nor deducted (a defective cup costs 4).

### Community Score (group sessions — trigger-authoritative)
```
totalCups         = Σ cups over the INCLUDED evaluations          (evaluations.cups, else the session's cupsPerSample)
uniformityPenalty = 2 × Σ nonUniform × 5 ÷ max(5, totalCups)
defectPenalty     = 4 × Σ defective  × 5 ÷ max(5, totalCups)
communityScore    = avgRawScore − uniformityPenalty − defectPenalty
```
- `totalNonUniform` — non-uniform cups of evaluations with 2+ cups, defective ones included (a defective cup is in both arrays and costs 6, same as the individual score)
- `totalDefective` — defective cups
- Both are summed per evaluation after clamping to that evaluation's cups.
- Computed by PostgreSQL trigger `trg_recompute_aggregate` on `evaluations` table (function re-issued by **PHASE 26**); written to `aggregate_scores`
- TypeScript function `calcCommunityScore()` in `lib/scoring.ts` is **display-only** — trigger result is authoritative; `tests/scoringConsistency.test.ts` ports the SQL arithmetic (same operation order, 15-digit numeric cast) and `tests/db/aggregate.dbtest.ts` runs the real trigger against `computeGroupAggregate` at every cup count 1–8. Change SQL and port in one commit.

Verification: 2 participants, cupsPerSample=5, 1 non-uniform-only cup → uniformityPenalty = 2×1×(5/10) = 1.0 ✓. 1 person with 2 cups, 1 defective → −6; 4 people × 2 cups, 1 defective → mine −6, session −3.75 (6 × 5/8).

## Supabase Manual Steps

Changes that Prisma migrate does NOT handle must be applied manually via the **Supabase Dashboard → SQL Editor**:

- RLS policies and policy updates
- Trigger functions (`recompute_aggregate_score`, etc.)
- `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`
- `ALTER TABLE ... REPLICA IDENTITY FULL`
- Enable **"Allow anonymous sign-ins"** (Dashboard → Authentication → Sign In / Up) — required for the guest QR-join flow (`supabase.auth.signInAnonymously()` in `components/join/GuestJoinForm.tsx`)
- Apply the **PHASE 14** `handle_new_user()` redefinition in `prisma/sql/rls_and_triggers.sql` **before** enabling anonymous sign-ins above — otherwise an anonymous user's NULL email hard-fails the profile insert. (The block is labelled PHASE 14 in the file; earlier revisions of this guide called it PHASE 13.)

These are all collected in `prisma/sql/rls_and_triggers.sql`. Append new blocks to that file and apply the new block manually each time. Every manual step gets a click-by-click section in **`docs/LAUNCH-RUNBOOK.md`** in the same PR (PHASE 18 = runbook §1).

**RLS policy rules (learned the hard way, PHASE 18):** never write `USING (true)` without a `TO authenticated` clause — a policy with no `TO` applies to the `anon` role, and the anon key is public. New helper functions get `SET search_path = public` and `REVOKE EXECUTE … FROM PUBLIC, anon` (they are reachable via `/rest/v1/rpc/*` otherwise) — but **any function an RLS policy calls must keep EXECUTE for `authenticated`**: policy expressions run as the querying role, and revoking it broke every Realtime subscription on 2026-09-14 (PHASE 18b). Check the Supabase **Security Advisor** after every SQL change.
**PHASE 25 (S9-02, A-10; file + dry run only until the owner applies it, runbook §28):** `session_participants` has table-level SELECT revoked and only `"sessionId"`, `"userId"`, `status`, `"joinedAt"` granted to `authenticated`, so the exclusion trail (`excluded_from_results`, `excluded_at`, `excluded_by`, `exclusion_reason`) is invisible over PostgREST. It is safe because only SECURITY DEFINER code (`recompute_aggregate_score`, the helpers) and Prisma read those columns; a querying-role policy must NEVER read them, and a new column on the table needs an explicit column GRANT in a later phase (`tests/phase25Sql.test.ts`).
**Since PHASE 24 the API roles are read-only across `public`:** no policy other than `FOR SELECT … TO authenticated`, no INSERT/UPDATE/DELETE/TRUNCATE grant for `anon`/`authenticated` on any table, and the default privileges of `postgres` make every new table born read-only for them. A table the browser must write needs an explicit `GRANT` + policy in its own SQL phase (`tests/phase24Sql.test.ts` replays the file and fails on any write policy). Two policies must never read each other's tables (PHASE 16's `coffees_select` <-> `coffee_shares_select` loop gave `42P17` on every select as `authenticated`): break the loop with a SECURITY DEFINER helper that keeps EXECUTE for `authenticated`, as `is_coffee_owner` does.
