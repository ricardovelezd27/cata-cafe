# Reference sample

### Reference Sample ("Referencia", 2026-09)
- The owner marks ONE sample per session as the control the others are compared against: `CuppingSession.referenceSampleId` (named relation `SessionReferenceSample`, `onDelete: SetNull`, list back-relation `SessionSample.referencedBy`). **Never** model it as a boolean on the sample and never let scoring, `computeGroupAggregate`, the SQL trigger or `AggregateScore` read it — it is display-only context ("el puntaje necesita contexto", PRODUCT.md).
- Writes: `setReferenceSample(sessionId, sampleId | null)` in `app/actions/sessions.ts` (`run()` → `ActionResult`, `requireSessionOwner` + `assertSessionWritable`, and a same-session `findFirst({ id, sessionId })` guard because the FK alone accepts any sample id). Create paths take `referenceIdx` (index into `samples`, validated by `parseReferenceIdx`) and stamp it via `applyReferenceByPosition` inside the same `$transaction` as the nested sample create; `duplicateSession` remaps by position. `removeSessionSample` needs nothing (SET NULL).
- Reads/UI: `cup/page.tsx` → `session.referenceSampleId` prop; `CupClient` keeps it in state and updates it from a `cupping_sessions` UPDATE handler on the existing `session:<id>` realtime channel (the table is already in the publication — no new SQL); `WaitingRoomClient` does the same on its channel. Results derive `SampleResult.isReference` in `results/page.tsx` and compute Δ with `lib/referenceDelta.ts` (`pickDisplayedScore` MUST mirror `ResumenTab.rankFor` so a Δ always uses the score shown beside it). PDF/print carry `isReference` → "<label> · Referencia".
- Strings with an ICU `{label}` arg that are rendered in client components (`cupping.compareHint`, `waiting.referenceLine`, `session.newForm.referenceMark`) are fetched with `t.raw()` and replaced client-side — calling `t()` without the arg renders the raw key.
- **ORDER (2026-09-25)**: the reference is cupped FIRST. `orderReferenceFirst` (`lib/referenceRules.ts`) puts it ahead of the rest, who keep their position order; every list site applies it — `cup/page.tsx` + `CupClient`'s sample tabs/Anterior-Siguiente, the results tables/radar/owner matrix (`results/page.tsx`), the CVA PDF route, the print page, and `lib/closeEmail.ts`. If the owner changes the reference mid-session, `CupClient.applyReferenceOrder` re-derives the order live from the `cupping_sessions` realtime handler and keeps the cupper on the sample they were viewing (matches by id, not by index).
- **PIN (2026-09-25)**: the reference's affective quality is fixed at 5 ("ni alto ni bajo") on all eight attributes and its cup checks are cleared, so every cupper's reference score is exactly 79.00 and only the descriptive side stays editable — affective and combined formats only (`isPinnedModule`; descriptive-only sessions have no quality ratings, so nothing changes). Enforced server-side on EVERY save of that sample in both write paths (`upsertEvaluation` and offline `syncEvaluation`, gated by the `referenceSampleId` that `requireSample*` now returns — a tampered client cannot move the anchor) via `pinReferenceAffective`. Mirrored client-side: `AffectiveForm`/`CombinedForm` take `lockedAffective` (bubbles disabled, cup grid replaced by a note, explanatory banner). The first time a cupper opens the reference, `CupClient` queues one pinned auto-save so their 79.00 exists even if they never touch it; scores entered before the lock existed are never rewritten (lock only applies going forward). Results treat the reference as an ANCHOR — excluded from the ranking, the session average and "Mejor muestra" (`ResumenTab`), shown instead as a standalone card above the ranking; the Δ chips still compare every other sample against it.
- **MULTI-REFERENCE (2026-10, S6)**: references accumulate. `SessionSample.referenceRank Int?` (1..3, `@@unique([sessionId, referenceRank])`, backfilled from `referenceSampleId` = rank 1); `CuppingSession.referenceSampleId` is ALWAYS the ACTIVE reference (highest rank), so pin/order/realtime/default Δ are unchanged. Pure rules in `lib/referenceRules.ts` (`referencesOf`, `activeReferenceId`, `orderReferencesFirst`, `planAddReference`, `planRemoveActive`, `compactReferenceRanks`, `nextReferenceOrder`, `resolveCompareReference`). `setReferenceSample`: new sample → `rank = max+1` (a 4th → `invalid_input`) + re-pin of that sample only; existing reference → no-op; `null` → drops only the active, previous becomes active. Only the ACTIVE reference is pinned (`isPinnedModule` keyed on `referenceSampleId`); earlier references keep their pinned data but unlock. When one becomes ACTIVE again (`null` drops the active one, or `removeSessionSample` removes its sample) it is pinned again, but never silently (S8-27): `countRepinOverwrites` (= `planReferenceRepin(...).length`, stored rows not already at the 79.00 anchor) decides — `setReferenceSample(null)` throws `conflict` unless `confirmRepin` is true (cup master panel + edit form ask via `ConfirmDialog` naming the sample and the evaluation count), and `removeSessionSample` (via `removeSamplesInTx`) rolls back with `reference_repin_required` (localized, "change the reference first"); with nothing to rewrite both just proceed. `removeSessionSample` compacts ranks and re-aims the pointer. Clients only get the active pointer over realtime, so cup/waiting derive the ordered list with `nextReferenceOrder` (append unknown id, truncate on a known one). Results: `SampleResult.referenceRank` (+ derived `isReference`); ranking/average/best exclude ALL references; the "Comparar con" selector (`localStorage` `cata_results_ref`, active by default) picks the Δ basis. Never read any of this from scoring, the trigger or `AggregateScore`.
- **REFERENCE MODE (S10 WP2, B1)**: `CuppingSession.referenceMode` = `"anchor"` (default; every existing session; the pin / 79.00 behaviour described above, a Café Sensible class exercise, NOT the CVA) or `"free"` (everyone scores the reference like any other sample; the others are compared with its average). Everything above about the PIN holds only in anchor mode, and **every** place that pins or locks goes through ONE predicate, `shouldPinReference({ mode, moduleKey, isActiveReference })` (`lib/referenceRules.ts`): `upsertEvaluation`, `replayEvaluationCore` (offline), `setReferenceSample` (re-pin planning AND the `confirmRepin` conflict), `removeSamplesInTx`'s reactivation re-pin, and `CupClient` (`isPinnedReference` -> `pinForReference`, `isCurrentLocked`, the first-visit pinned auto-save, the re-pin confirmations). The server reads the mode from the session row (`requireSample*` / `requireSession*` return `referenceMode`); the client value is only for the UI and `tests/referencePinGate.test.ts` fails when a file pins without `shouldPinReference`. The mode is chosen in the wizard when a reference is marked, changeable in the edit form only while `isFormatLocked` is false (else `format_locked`) and copied by `duplicateSession`. In BOTH modes references stay out of the ranking, the session average and "Mejor muestra" (`anchorsOf` unchanged); the results card, the help text, the master-panel hint, the edit helper and the participant-summary PDF tag say "anchor / 79.00" only in anchor mode. Never read `referenceMode` from scoring, the trigger or `AggregateScore`. **Wording (S10 WP6b)**: every surface that says "fixed reference / 79.00" decides it through `referenceExplanation({ mode, moduleKey })` (`lib/referenceRules.ts`; `referenceCopySuffix` picks the message key), i.e. by format AND mode: a descriptive session never claims a pinned 79.00 in either mode (`tests/referenceCopyDescriptive.test.ts`). `planFinish` is unchanged (a reference row alone never allows closing, in either mode).
- **B2 STASH (S10 WP5b, `TODO(kim-validar:B2)`)**: the pin never destroys a cupper's ratings. Whenever a pin overwrites stored affective input that is not already the anchor state, the previous values go inside the SAME module JSON under ONE key, `ref_previo` = `{ at, valores }` (`lib/referenceStashKey.ts`; `valores` holds every key `pinReferenceAffective` overwrites, the list `PIN_OVERWRITTEN_KEYS`: the eight `<attr>_final`, `tazas_no_uniformes`, `tazas_defectuosas`, `defecto_tipo`, `tazas_defecto_tipo`; `tests/referenceStashReview.test.ts` derives the list from the pin itself so a future key cannot be forgotten; `null` = the key was absent). Pure rules in `lib/referenceRules.ts`: `stashBeforePin(stored, pinned)` (an existing stash is NEVER overwritten: the first real values win), `restoreFromStash`, `planReferenceRestore`. The key is server-owned: `computeEvaluationDerived` strips it from every payload and attaches only the stash a trusted caller passes (`{ refStash }`), so a client can never set, change or delete it; it counts toward the 64 000-char module bound and is invisible to scoring, completeness, the trigger and every report. EVERY write path that pins reads the stored row and carries the stash: `upsertEvaluation` (one extra read, only for the pinned reference), the offline `replayEvaluationCore`, `planReferenceRepin` (the re-pin planning of `setReferenceSample`) and `recomputeLegacyDraftsInTx`; `removeSamplesInTx` writes no evaluation (it only refuses when a re-pin would overwrite), so it carries nothing. RESTORE: when a sample STOPS being the active pinned reference while the session is open (`setReferenceSample(null)` removes it, or naming another sample unlocks it), in the same transaction and anchor mode only, each of its evaluations holding exactly the anchor state gets its stashed values back (derived scores recomputed, `isDraft` echoed so a submitted row re-fires the aggregate); a re-rated one keeps its values and just drops the stash. `setReferenceSample` returns `{ referenceSampleId, restored }` and both callers show the non-blocking notice `session.edit.ratingsRestored`; the re-pin confirmations say the previous ratings are kept and come back. Free mode never pins, never stashes. **Review fixes (PR #136)**: (1) the page tells the server when a module was produced under the pin (`pinnedView` on `upsertEvaluation`, the offline module blob and `replayEvaluation`; the client marks the exact data object through a `WeakSet`, so a debounced or in-flight save keeps its flag). `lib/evaluationPinWrite.ts` `writeEvaluationPinAware` decides in ONE transaction that first takes a `FOR SHARE` lock on the session row (so `setReferenceSample`'s pointer update cannot interleave), re-reads the session's CURRENT active reference and mode and the stored module, then applies the pure `resolvePinnedPayload`: sample pinned now = pin and carry the stash (an existing stash wins; a payload holding REAL ratings, i.e. a cupper who was offline when the sample was marked, is stashed from the payload when no stash exists); not pinned now but `pinnedView` = every key of `PIN_OVERWRITTEN_KEYS` keeps the STORED value and the rest comes from the payload, no stash; otherwise an ordinary save. Only the pinned-at-authorization or `pinnedView` writes use the transaction; every other save stays the one-statement hot path. Client half: `reconcileUnpinned` (`lib/sampleReconcile.ts`) makes a sample that stopped being the pinned reference adopt the server's restored values for those keys on the next refresh (local descriptive edits stay, the offline draft is rewritten, the mark is dropped; offline, the server rule protects). (2) A RESTORE on a REVEALED sample is allowed (it puts back ratings the cupper gave blind, before the pin; it is not a new judgement); the reveal refusal (`pinWouldTouchRevealed`) runs BEFORE any stash, restore or re-pin write. (3) A restore never blocks the owner: a row whose stashed values fail validation stays pinned with its stash, is logged (`restore_skipped_invalid`, ids only) and is not counted in `restored`. (4) A restored row that was stored under the previous rule comes back scored under the current rule (the pin had already written `cups`). (5) **LOCK ORDER (`lib/sessionLock.ts`)**: where a transaction takes the session row, it takes it FIRST (then sample rows, then evaluation/aggregate rows). **Exclusive (`lockSessionRow`, `FOR UPDATE`)**: `setReferenceSample`, `removeSamplesInTx` (so `removeSessionSample` and `finishSoloSession`'s removal), `revealSample`, `renameSessionSample` and the label/prep write of `updateSampleMetadata`. **Shared (`lockSessionRowShared`, `FOR SHARE`)**: the flip of `submitAllEvaluations` and of `finishSoloSession`'s submit step, `refireAggregates` (exclusion, close, "Actualizar"), `acceptLateEvaluation` and `submitLateDraft`. **Shared too, since S10 WP6b**: a pinned or `pinnedView` save (`lib/evaluationPinWrite.ts`, through `lockSessionRowShared`). Both helpers run `SET LOCAL lock_timeout = '5s'` as the first statement of the transaction (it lasts for the WHOLE transaction, so every later lock in it also gives up after 5 s; all of those timeouts are mapped to `busy_retry`); a lock timeout (SQLSTATE 55P03, `lib/lockTimeout.ts`) becomes the typed code `busy_retry` (`classifyActionError` maps a raw 55P03 too), nothing is written, and `submitLateDraft` answers `pending` (the draft stays on the device). `refireAggregates` inside the close routine (`finalizeClosedSession` step) only logs the failure and leaves `closeFinalizedAt` null, so the cron repair retries it; the owner actions that call it (`setParticipantExclusion`, `refreshAggregateScores`) surface `busy_retry` and are safe to repeat. **NOT taking the session row**: an UNPINNED live save (the plain one-statement hot path of `lib/evaluationWrite.ts`), the re-fire after editing an already submitted evaluation (`submittedRefireArgs`), and the offline replay of an unpinned module. There is no cycle there: they update EXISTING evaluation rows, the aggregate row they fire already exists (the trigger's upsert updates it and takes no foreign-key lock on the sample row), and a first save inserts a brand-new evaluation row nobody can be waiting on. The first SUBMIT of a sample (no aggregate row yet, so the trigger INSERTS one and needs the sample key-share) is exactly the case the shared lock covers. Anything new that touches a session's reference, or that submits evaluations, must follow this (without it Postgres aborts one side with 40P01; `tests/db/referenceConcurrency.dbtest.ts` pins every pair with a deterministic interleave, and `tests/db/lockTimeout.dbtest.ts` pins the timeout). Measured before WP6b: under an unrealistic load (12 cuppers saving the reference back-to-back) the owner's change waited until the load stopped; with the real 800 ms debounce it took under 200 ms. A duplicate first save that hits the unique constraint inside the transaction is retried once OUTSIDE it. **S10 WP6b**: that pinned-save transaction takes the session row through `lockSessionRowShared`, so it waits at most 5 s too (`upsertEvaluation` answers `busy_retry`, the cup page keeps the save pending; the offline replay answers `pending`); `updateSampleMetadata` writes the coffee, the label and the prep data in ONE transaction behind `lockSessionRow` (a busy lock leaves nothing half saved), and it, `renameSessionSample` and `removeSessionSample` answer a thrown error as `{ ok: false, error: <ActionErrorCode> }` through `runFlat` (`lib/safeAction.ts`, keeps their existing result shapes). (6) The pinned-view mark survives a page reload (`lib/pinnedViewHydration.ts`): the flush-backup entry carries `pinnedView` (`backupEntryFor`), and the mount rehydration (`planHydration` -> `hydrateModule`) puts the mark back on the hydrated module and sample, or, when the sample is no longer pinned, applies the server-wins rule for the pin keys at once and rewrites the offline module. No server-side "looks like the anchor" heuristic: a cupper may legitimately rate all 5s.
