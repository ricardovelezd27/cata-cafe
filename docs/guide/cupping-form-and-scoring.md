# Cupping form and scoring

### Auto-Save in CupClient
`CupClient` debounces evaluation saves at 800ms. Do not add additional `revalidatePath` calls that would trigger a full re-render on every keystroke — the debounce exists to batch writes.

### Evaluation Data Shape

**Per-cup defect type (S10 WP1b, `TODO(kim-validar:A3)`):** the module JSON key `tazas_defecto_tipo` holds one entry per cup (length = the session's `cupsPerSample`), each a `SENSORY_DEFECTS` id (`moldy | phenolic | potato`) or `null`. It is JSON ON PURPOSE (no column, no migration). `computeEvaluationDerived` (the one derivation of the live save and the offline replay) is the only place that decides what counts: key ABSENT = legacy blob, stored exactly as posted (a flagged cup with no type still counts and reads "sin especificar"); key PRESENT = a flagged cup is ALWAYS defective, typed or not (an untyped one counts as "sin especificar"; a deduction already recorded never disappears because its type is missing, decision doc 5.3), a type on an unflagged cup is cleared, with 2+ cups a defective cup is forced non-uniform, and `defecto_tipo` / `Evaluation.defectTypes` are DERIVED from it (distinct NON-null types of the defective cups, in `SENSORY_DEFECTS` order). "A type is mandatory" lives in the FORM only: marking a NEW cup defective needs a type, a legacy flagged cup keeps its mark and the chip "Falta el tipo de defecto" (tappable to choose one), nothing but deliberately unmarking it removes it, and submit is never blocked by a missing type. `lib/cupDefects.ts` holds the pure readers/helpers: `defectTally(data, cups)` (the one reader of "which cups were defective and of which type"; reusable for the coffee lifetime tally), the form's `applyDefectChoice` / `applyNonUniformToggle` (the non-uniform row never removes a defect: on a defective cup the tap opens the type chooser and the helper changes nothing), and `formCupState` (seeds a legacy draft's flagged cups from its single legacy type; cups with no single type stay flagged and untyped). `pinReferenceAffective` clears the key too.
**Partial evaluations and the cooled value (S10 WP3b, `TODO(kim-validar:C4)` / `TODO(kim-validar:A5)`):** three more key families live in the affective/combined module JSON, no column. `<attr>_ne = true` (literal boolean only; any other value is dropped) means the cupper could not judge that section ("No evaluado"); `<attr>_inicial` (1..9, display-only) is the first value given before it cooled; `<attr>_final` stays THE only value that scores, completes and feeds the trigger. `<attr>` is an id of `AFFECTIVE_ATTRIBUTES`. All rules live in the pure `lib/affectivePartial.ts`: `isAffectiveDeclaredPartial` (at least one `_ne`, at least one rated, every section rated OR marked; `isAffectiveComplete` is unchanged, and an old incomplete row with NO marker is not a partial and behaves exactly as before), `applyNotEvaluated` (a marker deletes the section's `_final`, base and `_inicial` so a stale value is never read), `sanitizeCooledValues` (clamp, drop when equal to `_final`), and the form transitions. `computeEvaluationDerived` applies them in that order and stores `rawScore` / `individualScore` / `affectiveSum` NULL for a declared partial (never a 5-filled total). "Finished" for completeness, `isEvaluationComplete` (results state, close rules, solo auto-close) is complete OR declared partial; `hasIndividualScore` (`lib/scoring.ts`) is the one gate every surface uses before it prints or recomputes an individual total (a partial shows "Parcial · sin puntaje"). `pinReferenceAffective` clears `_ne` / `_inicial`. The optional timer is client only: `lib/cuppingTimer.ts` (pure cue/format rules) + `components/cupping/CuppingTimer.tsx`, the start timestamp in `localStorage` `cata_timer_<sessionId>_<userId>` (nothing else, cleared by `clearLocalDeviceState`), shown to the session's owner only, in the tasting info area left of the form on a desktop (OR-C, owner 2026-11-21: a participant has no timer). Review round: the SQL helper and `isAffectiveDeclaredPartial` read a rating ONLY when the JSON value is a number (no text cast, so an old odd row can never make the trigger raise); all eight sections marked is neither complete nor partial and completeness reports it as not finished (`isAllNotEvaluated`); the coffee profile's attribute merge weights a sample by `participantCount + partialCount` (`filterCoffeeSamples` counts the partials, a number only); the CVA form labels a declared partial `partialDeclared`.

### Form State Pattern
Cupping form components are fully controlled. State is lifted to `CupClient`, which orchestrates sample navigation, tab switching, and auto-save. Individual forms receive data and `onChange` callbacks as props.

### The deduction rule (S10 WP1a — one formula, three scopes)
The score that existed before S8 was right in principle and had bugs; S8-04 removed the deductions below five cups instead of fixing them. This goes back to the principle (flagged cups cost points at ANY cup count, and everyone's cups share the deduction) and fixes three bugs: (1) a cupper with fewer than five cups saw no deduction in their stored score; (2) with fewer than five pooled cups the stored group score amplified the deduction (1 defective cup of 2 cost 20); (3) a defective cup was counted twice in the group (8 points for 1 of 5; the CVA and the individual score say 6). It is not a new scoring system. Spec: `docs/product/cata-descentralizada-puntaje.md`.

```
S                 = 0.65625 × Σhᵢ + 52.75 − uniformityPenalty − defectPenalty        (rounded to 0.25, clamped 0..100)
factor            = 5 ÷ max(5, cups)
uniformityPenalty = 2 × nonUniform × factor
defectPenalty     = 4 × defective  × factor
```
- `hᵢ` — final value (1–9) for each of 8 affective attributes
- `nonUniform` / `defective` — flagged cups, counted independently from the two arrays and clamped to the evaluation's cups (`evaluationCupCounts`). A defective cup is ALSO flagged non-uniform by `AffectiveForm`/`CombinedForm`, so it sits in both arrays and costs 4 + 2 = 6. Never more than 6 per flagged cup.
- Non-uniformity exists only for an evaluation with 2 or more cups: with 1 cup it is neither counted nor deducted (a defective cup costs 4).
- `cups` — **individual scope:** that evaluation's cups (never more than five, so the factor is 1: the flat CVA deduction). **Session (group) scope:** the SUM over the INCLUDED evaluations of their cups, flags summed over the same evaluations: flat up to five pooled cups, diluted beyond. **Coffee lifetime scope (S10 WP1c, `TODO(kim-validar:A2)`):** every cup of that coffee across the sessions that count, computed at READ time by the pure `computeCoffeeLifetimeScore` (`lib/coffeeLifetimeScore.ts`), NEVER stored and never read or written by the trigger or `AggregateScore`; always the current rule (v2), even over evaluations stored before 2026-11 (their ratings and flags are data, only their stored totals are history). It runs over `filterCoffeeSamples`' survivors (closed session, revealed sample, excluded cuppers removed: no gate added or relaxed). Feed table (review fix H1): the coffee pools the cups and flags of exactly the evaluations a session's group score pools, the COMPLETE ones (`isAffectiveComplete`); an empty or partly filled evaluation feeds nothing (a coffee with one session always shows that session's deduction, property-tested against `computeGroupAggregate`). Descriptive format feeds nothing; a complete evaluation feeds the BASE (one voice, whatever its cups: `mean(calcRawScore)`) AND the cups/flags; a complete quick impression (session with exactly 1 cup per sample) feeds cups/flags only; EVERY reference sample of an `anchor`-mode session feeds nothing (pinned, not an opinion; the page says how many sessions were skipped: `anchorReferenceSessions`), of a `free`-mode session it counts as any other. `cups = evaluation.cups ?? session.cupsPerSample`, flags through `evaluationCupCounts`, deduction through `cupDeduction` over the SUMMED cups (same formula as every other scope), score through `calcCommunityScore` (`roundToQuarter`, clamp 0..100); `null` score when no evaluation feeds the base (the page still shows the tally). It also returns the tally through `defectTally` (by type, `unspecified`, non-uniform, % of cups, `foundBy` = DIFFERENT cuppers that flagged a defective cup). **No id leaves the server:** `filterCoffeeSamples` replaces every cupper by an opaque per-call index (`cupperKey`) in each sample's `lifetime` slice and the function's output is numbers only (tests pin both). `indicative` = fewer than 5 pooled cups (`lib/indicativeCups.ts`, ONE predicate also used by `RANKING_POLICY.indicativeBelowCups` for the session ranking and the ficha técnica, IN ADDITION to the cupper-count rule). The arithmetic line is NOT an equation (`Base 84.00 · Descuento 0.75 (1 taza defectuosa) · Puntaje 83.25` plus the fixed note that the score is rounded to the nearest quarter point) and says `defective` and `nonUniformOnly` (a defective cup is also flagged non-uniform: it must not read as two cups). Plain-language lines (`lib/coffeeLifetimeLines.ts`, `coffee.lifetime` messages + the equal `LIFETIME_COPY` for the PDF) render on the coffee page (`LifetimeScoreCard`) and the coffee ficha PDF; the per-session rows keep each session's stored number and the radar stays merged from session rows (quick impressions feed the radar but not the base).
- `cupDeduction({ cups, nonUniform, defective })` and `evaluationCupCounts(nonUniform, defective, cups)` in `lib/scoring.ts` are the only implementation: `calcIndividualBreakdown`, `computeGroupAggregate`, `calcCommunityScore`, the results page, `fichaTecnica` and the CSV/PDF all read them. There is no `MIN_CUPS_FOR_PENALTIES` / `penaltiesApply` gate any more and no formula copy anywhere else.
- `Evaluation.cups` (migration `20261113090000_evaluation_cups`, nullable) is the number of cups an evaluation covers, written by `computeEvaluationDerived` on every save (live and offline replay). It is NOT backfilled: **NULL = scored before the 2026-11 rule**. The trigger reads a NULL as the session's `cupsPerSample`.
- Scores stored before the deploy were computed under older rules and are NOT recomputed in bulk (owner's decision; "no past score ever changes": a closed session is the record of that day; only a deliberate re-fire of that sample recomputes it, see below); PHASE 23 STEP 2 and `scripts/resync-low-cup-history.ts` are CANCELLED and must never run.
- **Rule versions (`lib/scoreRule.ts`).** `ScoreRule = "v1" | "v2"`. v2 is the rule above. v1 is the rule before 2026-11 (deductions only from five cups per sample; group `totalNonUniform × 10/totalCups + totalDefective × 30/totalCups`, `totalCups = cupsPerSample × included`), kept as small labelled branches in `lib/scoring.ts` ONLY so past results render unchanged; new code never calls v1. The DATA says which rule applies, there is no cut-over date: `evaluationScoreRule(cups, isStoredRow)` is v1 only for a STORED evaluation with `cups` NULL (unsaved form data is always v2); `sampleScoreRule(aggregate, evaluationCups)` is v1 when a stored `AggregateScore` row has `ruleVersion = 1`; with NO row it is v1 only when the sample has stored evaluations and every one has `cups` NULL, else v2. `GroupEvalInput.rule` (from `evaluationScoreRule`) lets `computeGroupAggregate` compute the SD per evaluation so the "± SD" chip agrees with the owner matrix. `calcIndividualBreakdown` / `calcIndividualScore` / `computeGroupAggregate` take `opts.rule` (default v2). Every surface that recomputes a score in TypeScript (results page and client components, `lib/reports/*`, CSV, CVA PDF, print page, close-email CVA attachment) passes the rule from the data; `SampleResult.scoreRule` and `AggregateScoreData.rule` carry it to the client. `ScoreBreakdownPanel` prints a neutral "previous rule" line for v1.
- `AggregateScore.ruleVersion` (`INTEGER NOT NULL DEFAULT 1`, same migration): existing rows stay 1; the PHASE 26 function writes 2 in its INSERT and its ON CONFLICT UPDATE. Consequence, intended: a re-fire of an old sample (a deliberate owner exclusion/inclusion, or a guest claim, see below) recomputes it under v2, stamps `ruleVersion = 2`, and the screen follows from then on. The close/repair/finalize pass does NOT re-fire an old sample (see `keep-old-rule` below). **One remaining exception, a decision the ARCHITECT took (the owner must be told):** when a guest claim removes or replaces an evaluation of a sample, that sample's group score is recomputed, and the only function that exists computes the current rule; an old sample in that situation moves to the current rule. `mergeGuestData` re-fires only the SAMPLES whose included evaluation set changed (`samplesToRefireAfterMerge`, `lib/guestClaimToken.ts`: the conflicted samples where the evaluation the merge DELETES was submitted (a conflict that only removes a draft recomputes nothing: a submitted row always beats a draft), plus, when the merged exclusion flag differs from the one an identity's evaluations were counted under, that identity's submitted samples); every other sample of those sessions is left as stored. `refreshAggregateScores` ("Actualizar") is a NO-OP on a closed or expired session, so a routine click never rewrites a past score. A draft saved before the deploy (cups NULL) and submitted after it is rewritten under v2 right before the flip (`lib/legacyDrafts.ts`, called by `submitAllEvaluations` and `finishSoloSession`). Editing a stored v1 evaluation writes `cups` and so also moves THAT evaluation to v2 (its `individualScore` is rewritten by the same save). ### Community Score (group sessions — trigger-authoritative)
```
totalCups         = Σ cups over the INCLUDED evaluations          (evaluations.cups, else the session's cupsPerSample)
uniformityPenalty = 2 × Σ nonUniform × 5 ÷ max(5, totalCups)
defectPenalty     = 4 × Σ defective  × 5 ÷ max(5, totalCups)
communityScore    = avgRawScore − uniformityPenalty − defectPenalty
```
- `totalNonUniform` — non-uniform cups of evaluations with 2+ cups, defective ones included (a defective cup is in both arrays and costs 6, same as the individual score)
- `totalDefective` — defective cups
- Both are summed per evaluation after clamping to that evaluation's cups.
- Computed by PostgreSQL trigger `trg_recompute_aggregate` on `evaluations` table (function re-issued by **PHASE 26**, and by **PHASE 29** (S10 WP3b), which is the LIVE body: the PHASE 26 body with ONE changed clause, the WHERE of the per-attribute averages, which now counts the complete evaluations AND the declared partial ones through `is_affective_declared_partial`); written to `aggregate_scores`
- **PHASE 29 status:** the dry run was executed in production on 2026-11-13 22:36 UTC (every line as expected: 0 evaluations with a marker, 0 with a non-numeric rating) and PHASE 29 was APPLIED on 2026-11-13 23:36 UTC on the owner's explicit yes, verified read-only (helper present, not executable by `authenticated`/`anon`, the trigger function mentions it, 354 aggregate rows all `ruleVersion` 1, none recomputed). It is live: never edit the PHASE 29 block or its dry run; a change is a new phase.
- **Partial evaluations in the group numbers:** a declared partial ("no evaluado" in some section) is submitted but NOT included: the total, `participantCount`, the cup pooling, the deductions and the SD use the complete evaluations only. It feeds only `attrAverages` (radar), each attribute averaged over the evaluations that RATED it (SQL `AVG` skips NULLs; TS `attrAveragesV2` in `computeGroupAggregate`, v2 branch only, the v1 branch is byte-identical). `tests/scoringConsistency.test.ts` ports the clause, `tests/phase29Sql.test.ts` diffs the PHASE 26 and PHASE 29 bodies (exactly that clause), `tests/db/partialEvaluation.dbtest.ts` runs the real trigger and helper.
- TypeScript function `calcCommunityScore()` in `lib/scoring.ts` is **display-only** — trigger result is authoritative; `tests/scoringConsistency.test.ts` ports the SQL arithmetic (same operation order, 15-digit numeric cast) and `tests/db/aggregate.dbtest.ts` runs the real trigger against `computeGroupAggregate` at every cup count 1–8. Change SQL and port in one commit.

Verification: 2 participants, cupsPerSample=5, 1 non-uniform-only cup → uniformityPenalty = 2×1×(5/10) = 1.0 ✓. 1 person with 2 cups, 1 defective → −6; 4 people × 2 cups, 1 defective → mine −6, session −3.75 (6 × 5/8).

### Where the rule is applied and displayed
A submitted evaluation edited later (`upsertEvaluation`, `syncEvaluation`) ends with `updateMany(submittedRefireArgs(id))` (`lib/aggregateRefire.ts`) so the trigger re-fires; `closeSessionInternal` calls `refireAggregates` (`lib/aggregates.ts`) before the history sync, in mode `keep-old-rule` (a sample is SKIPPED when it has no aggregate row with `ruleVersion` other than 1 AND no submitted evaluation with `cups` set, i.e. no row or a v1 row, all evaluations stored before the deploy: the close/repair/cron pass never writes or rewrites a pre-deploy score, and never gives a first score to a sample that has no row; a v2 row or any evaluation with `cups` re-fires it; truth table in `lib/aggregates.ts`); the deliberate owner actions (`setParticipantExclusion`, `refreshAggregateScores` on an open session) use mode `full`. A draft saved before the deploy (`cups` NULL) is recomputed at submit by `lib/legacyDrafts.ts`: `hasLegacyDrafts` runs outside any transaction and only when it finds one do `submitAllEvaluations`/`finishSoloSession` open a transaction (`{ maxWait: 10_000, timeout: 30_000 }`); otherwise the flip is the plain `updateMany`. History: `communityScore` is null without an included evaluation, and a "quick impression" is a session with exactly ONE cup per sample (`QUICK_IMPRESSION_CUPS`, `isQuickImpression` in `lib/historyRules.ts`; owner's decision 2026-11-12, display-only tag; TODO(kim-validar:A3)). `CupToggleGrid` always shows the one-line cost of a flagged cup (`copy.scoreHint` / `copy.scoreHintGroup` of `CupToggleGrid`, from `cupping.cups.*`); the sentence "Tus tazas se suman a las del grupo…" is part of it ONLY in group sessions. The results breakdown (`ScoreBreakdownPanel`) prints the penalties carried by the page's data (the TypeScript recompute, or the stored row when nothing was recomputed) and shows the formula only when it reproduces them (samples under the old rule print just the name).

### Consensus (SD)
`computeGroupAggregate` also returns `scoreSd` — the population standard deviation (÷n) of the included cuppers' individual CVA totals, `null` when fewer than 2 evaluations are included. Display-only, like `communityScore`; the DB trigger is untouched. Shown as a neutral "± X.X" chip next to the community `ScorePill` in the Resumen ranking, and as a "DE" column in the owner's CVA matrix (`OwnerParticipantSection`, reusing its existing `rowStats`).
