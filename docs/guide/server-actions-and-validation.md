# Server actions and validation

### Server Action Contract (2026-09 error-handling foundation)

- **`runFlat(name, fn, ctx)`** (`lib/safeAction.ts`, S10 WP6b): the variant of `run()` for an action whose result is already a flat `{ ok: boolean, ... }` object that its callers read directly. It keeps that shape untouched on success, and on a thrown error returns `{ ok: false, error: <ActionErrorCode> }` (logging `unknown` ones), letting `redirect()`/`notFound()` through. Use it only to wrap an existing flat-shaped action without changing its callers; a new action returns `ActionResult` through `run()`. Today: `renameSessionSample`, `removeSessionSample`, `updateSampleMetadata`.
- **S8-14**: group roster/post actions and the insight actions (`runInsight`, `runPivot`, `saveInsight`, `deleteSavedInsight`, `runBenchmark`, `runOriginContext`, …) follow this contract. `group_full`, `invalid_email` and `offline` were added (`offline` is raised client-side by `feedback.run` when `navigator.onLine === false`). Background auto-runs (debounced explorer/pivot) toast only `isAccessError` codes. A server page never calls an action for a read: `lib/analytics/savedInsights.ts` is the read helper.
- **Digest + chat quota (S8-14)**: the monthly digest claims its `digest_runs` period as `running` BEFORE sending and releases it when nothing was sent (`lib/digestClaim.ts`); the insights-chat question slot is reserved atomically before the model loop and released when no model call succeeded (`lib/ai/chatQuota.ts`). Group email links never carry the recipient address. The founding cohort size is `FOUNDING_SEATS` (`lib/landing/founding.ts`), copy only, never enforced.

### Validation

- **Dates stay inside years 0000..9999 (audit J-01, 2026-11-16)**: a production session had `closesAt` in the year 20228 (a pre-S8-05 typo); Postgres stores it, but the Date read back cannot be serialised and `toISOString()` threw inside the sessions list, so the whole page fell into the error boundary. `isPlainIsoDate` (`lib/safeDate.ts`) is the range rule: `isoDate` and `dateOnlyEndOfDay` refuse anything outside it (and a day that rolls over, "2026-02-31"), `endOfDayInZone` refuses a day that is not `isCalendarDay` or is after `LAST_CLOSING_DAY` (both paths answer `invalid_closes_at`), and the date inputs carry `max` (`MAX_DATE_INPUT` / `LAST_CLOSING_DAY`). Server pages serialise session dates with `toIsoOrNull(date, { where, field, sessionId })`: an unserialisable date becomes null and is logged (`unserialisable_date`, ids only), so one bad row never takes a list down. Use it for any new `toISOString()` on a stored date that reaches a list.
