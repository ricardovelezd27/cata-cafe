# Session lifecycle

### Session Lifecycle (see docs/flows.md for diagrams)

- **No re-dating (Kim C9)**: `updateSession` refuses ANY change on an expired session (`canEditSessionSettings`), the edit page is read-only. **Idle live sessions (Kim C3)**: owner reminder at `LIVE_IDLE_MS` = 24 h, automatic close after `LIVE_AUTO_CLOSE_MS` = 7 days idle (`isLiveAbandoned`; "activity" = an evaluation being saved) by a bounded cron pass (`closeIdleLiveSessions`, `lib/idleClose.ts`, `CloseReason` `"idle"`, 5 per run, run AFTER the deadline closes, repairs and reminders and before the always-last ledger purge (**every pass is isolated, S10 leftovers B3**: `runPass` in `lib/cronPass.ts` wraps the deadline-close and repair passes (candidate query included), a throw is logged with a code only, flagged `closeFailed` / `repairFailed` / `remindersFailed` / `idlePassFailed` in the JSON and the later passes still run), no new close after `CRON_CLOSE_START_BUDGET_MS` = 150 s; summary `idleClosed` / `idleClosedSilently` / `idleTruncated` / `idleBudgetTruncated`). **Backlog rule**: `idleCloseDecision` (`lib/closeRules.ts`) — idle 7 to under 30 days closes with `emails: "await"`, `IDLE_SILENT_CLOSE_MS` = 30 days or more closes with `"skip"` (no email, still finalized) so the first production run never mails abandoned sessions. The expired-not-closed OWNER gets "Cerrar ahora" on the results page (`canCloseNow`, `closeSession`). `viewerMayReadGroupResults` (`lib/sessionState.ts`) is the ONE call site of `canViewGroupResults` (results page and participant-summary route); the cup page's `submittedCount`/`submittedOf` go through `cupGroupProgressForViewer` (owner only); history rows of an open group session carry no community score (`historyCommunityScoreForSession`); the group activity feed shows submissions of closed sessions or sessions the viewer owns.
- **Idle auto-close and the grandfather rule (S10 WP4a, Kim C3, `TODO(kim-validar:C3)`)**: the cron closes a live group session idle (since max(`startedAt`, last evaluation update)) through ONE pure rule, `idleCloseDecision({ startedAt, idleMs })` in `lib/closeRules.ts`: started on/after `IDLE_RULE_EFFECTIVE_AT` (2026-11-18 UTC): <7 d none, 7 to <30 d emails, 30 d or more silent (`emails: "skip"`); started BEFORE it ("grandfathered", owner decision): <30 d none, 30 d or more silent, NEVER emails, and no new `live_idle` reminder (`shouldSendLiveIdleReminder`, query `startedAt >= IDLE_RULE_EFFECTIVE_AT`). The candidate query (`idleCandidateBands`), `isLiveAbandoned`, the repair rule (`repairEmailMode`/`closedSilently`, which also stays silent when `createdBy` is a deleted-account placeholder) and the results-page "closed silently" line all go through it; the cron passes ONE `now` to the reminder and idle passes. The PHASE 28 dry run carries the effective date as one literal (lines 2a/2b/2c; `tests/closeRulesGrandfather.test.ts` checks it equals the TS constant). Runbook §33.
- **S10 WP4b (Kim C1 / C2, `TODO(kim-validar:C1)` / `TODO(kim-validar:C2)`, migration `20261115100000_close_notice_and_late_contributions`, runbook §36; five nullable columns, no SQL phase: `cupping_sessions` and `evaluations` are table-granted)**: (1) **announced close** — `announceClose(sessionId, 2|5)` / `cancelAnnouncedClose` (owner, group, `assertSessionWritable`, `ActionResult`) set/clear `CuppingSession.closingAt`; display only, NO server enforcement and no cron: the owner's open cup page calls `closeSession` when it watches the countdown reach zero (`shouldAutoClose`), a page opened after it passed says "El cierre anunciado ya pasó" with "Cerrar ahora" / "Cancelar"; `closeSessionInternal` never touches the column; cuppers get a polite banner (`CloseAnnounceBanner`, fed by the `cupping_sessions` realtime UPDATE and the page's `closeNotice` {closingAt, serverNow}, skew-corrected like the warm-up run; pure rules in `lib/closeAnnounce.ts`); the close dialog is `CloseSessionDialog` (now / 2 min / 5 min). (2) **late evaluations** (sanctioned post-close write: `acceptLateEvaluation`) — `acceptLateEvaluation(evaluationId)`: registered, resolved evaluation -> sample -> session on the server, caller must OWN the session, `isAcceptableLate` (`lib/lateContributions.ts`: session `closed`, a DRAFT, COMPLETE by `isEvaluationComplete`; a guest passes, a deleted-account placeholder and an excluded cupper do not); one transaction (row lock, `recomputeLegacyDraftByIdInTx` for a `cups` NULL draft, then `isDraft=false` + `submittedAt` + `acceptedLateAt`), the trigger recomputes THAT sample only, then history re-sync; idempotent; `acceptedLateAt` also moves "Resultados actualizados el" (page + `sessionReportData`). The owner's `LateEvaluationsPanel` rows exist ONLY in the owner lens payload (`buildOwnerLateRows`); a cupper gets only their own "no se envió / se incluyó" lines (`buildMyLateNotices`). (3) **note left on the device** (sanctioned post-close write: `submitLateDraft`) — `submitLateDraft` (`app/actions/offline.ts`, member, CLOSED group session only, `requireUserExpecting`) writes a DRAFT only, never over a submitted row (`planLateDraftWrite`), never `isDraft`/`submittedAt`/`acceptedLateAt`; `UnsyncedNotesPanel` offers "Enviar al organizador" for a complete module (`isModuleSendable`). (4) **note after close** (sanctioned post-close write: `setPostCloseNote`) — `setPostCloseNote(evaluationId, text, expectedUserId?)`: the cupper's OWN SUBMITTED evaluation of a CLOSED session, text only, max 500, writes only `postCloseNote` / `postCloseNoteAt` (the trigger does not fire); read by that cupper and the session owner only (`buildPostCloseNotes`), never in a report tier or the CSV. **Review fixes (PR #131; fifth nullable column `evaluations."receivedLateAt"`, same migration)**: after the close every coffee is revealed and everyone sees the group results, so a late evaluation may have been written knowing the answer, and the organizer must accept it INFORMED and accept exactly what they saw. (a) `submitLateDraft` stamps `receivedLateAt` (create and update; the server's own record, nothing the client sends decides it) and `planLateDraftWrite` never replaces a draft the server already had at the close (`receivedLateAt` NULL: answer `conflict`, reason `saved_before_close`, panel copy "El organizador ya tiene la versión que guardaste antes del cierre."); a draft that itself arrived late is updated only if newer; a submitted row is `conflict` (reason `submitted`). (b) Each late row (owner lens only) shows the evaluation's own total (`individualScore`, "parcial" if null), the difference from that sample's current group score, the 8 ratings on demand, and ONE label decided by `receivedLateAt`: "Guardada antes del cierre" or, with the `warning` token plus an icon, "Recibida después del cierre: pudo escribirse después de ver los resultados."; the confirm dialog repeats score and label, and adds the previous-rule sentence when the sample's stored aggregate is under rule v1 (`oldRule` boolean from `sampleScoreRule`). (c) **Version guard**: `acceptLateEvaluation(evaluationId, expectedUpdatedAt)` compares the locked row's `updatedAt` (ISO, ms kept) with the one the page rendered and answers `conflict` (nothing flipped; the panel says "Esta evaluación cambió. Recarga para ver la versión actual." and refreshes). (d) An **excluded** participant (`excludedFromResults`) is not listed, `isAcceptableLate(…, { excluded })` refuses it (`invalid_input`) and they get no "se incluyó" line. (e) **`closeAnnounced(sessionId, closingAt)`**: the owner page's zero-countdown calls this, never the plain close; the server closes ONLY if the stored `closingAt` equals that instant and it has passed (2 s tolerance), else ok with `closed: false`; "Cerrar ahora" stays `closeSession`; `shouldAutoClose` never fires while a cancel runs or after "Cancelar". (f) Cupper banner: counting, then "está por cerrar" for at most 2 min past zero, then "El cierre anunciado no se hizo. La cata sigue abierta." for 10 min, then nothing (`bannerState`). (g) `setPostCloseNote` writes its two columns and Prisma's `@updatedAt` moves; nothing reads `Evaluation.updatedAt` of a submitted evaluation of a closed session (the only readers are the idle-close activity scan on open sessions and the guest-claim tie-break, which uses `submittedAt` for submitted rows). (h) Account deletion sets `postCloseNote` / `postCloseNoteAt` to NULL when the evaluations move to the placeholder; a guest-claim conflict that deletes the losing evaluation loses its note (accepted, documented). **Ranking honesty (S8-12)**: community numbers are shown with "n de N incluidos" and the `RANKING_POLICY` flags from `lib/reports/ranking.ts` (shared ranks, "indicativo" with 3, 4 or 5 included cuppers and firm from 6 (S10 WP5b, D3), no SD/"mejor" under 3, the gap rule `hasNoClearGap` / `RANKING_POLICY.gapFloor` ("sin diferencia clara" when neighbours are closer than the LARGER of 1 point and half the larger sample SD) is NO LONGER SHOWN on the results page (the owner, 2026-11-21: a ranking orders and does not compare) and is read only by the participant-summary PDF; `TODO(kim-validar:D3)`) — display-only, never read by scoring, the trigger or `AggregateScore`. Reports carry `ReportStamp` (`lib/pdf/stampText.ts`) and the owner has `/api/sessions/[id]/results-csv`.
- **Express ("Catar ahora", 2026-10)**: `createExpressSession` (`run()` → `ActionResult`, rejects guests) creates a solo session from a phone in three taps — name · format · 1–20 samples — with `cupsPerSample: 1` and **coffee-less samples** (`coffeeId: null`, labels "Muestra A…", rules in `lib/expressSession.ts`). Coffee-less samples are legal everywhere (`duplicateSession` already produced them); only the full wizard's `validateSessionInput` requires a coffee. The "Notas rápidas" end step was REMOVED for everyone (owner, 2026-11-21: final notes are asked in the Global step): the last sample's footer button submits through `handleGoToResults`, unchanged. Stored `nota_express` values (`EXPRESS_NOTE_KEY`, inside the format's module column, never counted by completeness, never read by scoring) still render where they did (results drill-down and the print page; the CVA sheet PDF follows the official SCA form since 2026-11-21 and prints no quick note, score line, session field, prep line or appendix page); nothing writes new ones. `updateSampleMetadata` never mints a "Sin nombre" coffee on a label-only save.
- Solo: `createSession` sets `status:"active"`; `submitAllEvaluations` **auto-closes** once the owner has a submitted evaluation for every sample. The ONE manual path is `finishSoloSession` ("Terminar cata", S8-05): it submits the owner's complete drafts, removes only evaluation-less samples (`lib/sampleRemoval.ts`) and then calls `closeSessionInternal` (so "close goes through the single routine" still holds). Do not add another.
- Group: active → `startedAt` via `startSession` (idempotent `updateMany where startedAt: null`; exposed on wizard step 2 AND the master panel's "Iniciar cata") → closed via owner `closeSession` or the cron once `closesAt` passes. **`closesAt` semantics (2026-09-25, zone-aware since S8-05):** the wizard posts a date-only `YYYY-MM-DD` plus the browser's IANA zone (`closesAtZone`); `validateSessionMeta` and `planClosesAtChange` turn it into the END of that day in THAT zone via `endOfDayInZone` (`lib/closeRules.ts`; null zone = UTC, the legacy rule; never `new Date("YYYY-MM-DD")`, which is 00:00 UTC and made the daily 06:00 UTC cron close the session the morning OF the chosen day). The edit form reads the day back with `dateInZone(closesAt, closesAtZone)`. So date D → closed by the cron on D+1 ~06:00 UTC; picking today is valid; setting any date also flips `isAsync` (no waiting room / "Iniciar cata"). The owner CAN change or clear it after creation: `updateSession` → `planClosesAtChange` (`lib/sessionState.ts`; group sessions only, else `not_group_session`; a day already over is `invalid_closes_at`; the stored day re-posted is a no-op; clearing it sets `isAsync = false`; a `closed` or expired session is refused with `session_closed` before this runs, S10 WP4a). For a live cupping the owner leaves it EMPTY and closes manually.
- **Delete keeps history**: `deleteSession` runs `detachCoffeeHistoryForSession` in the same transaction — every cupper keeps a `UserCoffeeHistory` row per sample they submitted: a coffee row for a REVEALED coffee-linked sample, and a LABEL-ONLY row (`coffeeId` NULL, `ensureLabelRows`, S8-16) for a never-revealed blind sample (so the coffee name never leaks, S8-02) or a coffee-less sample — each with a `snapshot` of their OWN evaluation + session metadata; `sessionId`/`evaluationId` are nullable `SetNull`. Readers must handle `session: null` (fall back to `snapshot`, no link). Coffee records are never touched by a session delete. `getDeleteImpact` feeds the confirm dialog (coffees + owners, cupper/evaluation counts). **`detachCoffeeHistoryForSession` must null `sessionId`/`evaluationId` itself before the delete** — the DB's `ON DELETE SET NULL` is not enough because rows written in the same transaction get every FK re-checked by Postgres, after the evaluation cascade already ran (P2003 on `user_coffee_history_evaluationId_fkey`, found 2026-09-24).
- `status` values in the wild: "active" | "closed" (+ legacy "draft"/"open" rows render as neutral/active in `StatusPill`).
- **Cron routes** (`app/api/cron/*`): `runtime = "nodejs"`, `dynamic = "force-dynamic"`, `maxDuration`, 503 when `CRON_SECRET` is unset, 401 on a bad `Authorization: Bearer`, bounded batch per run, JSON summary. Register in `vercel.json` and document the manual check in `docs/LAUNCH-RUNBOOK.md`.

### S8-21 loose ends
- Master-panel re-pin asks (`ConfirmDialog`, `session.edit.repinBody`) when the chosen sample already has evaluations (`evalCountBySample`, owner-only prop from `cup/page.tsx`); `confirmRepin: true` is sent only after the owner confirms.
- The results page repairs a SOLO owner's closed-but-unfinalized session once per render (`soloRepairOwedOnView`, 20 s grace `ON_VIEW_REPAIR_GRACE_MS` so it never overlaps a close in flight, failure only logs); group sessions stay with the cron (emails). `closeSession` returns `finalized`; `false` shows a non-blocking notice.
- `tests/registeredOnlyActions.test.ts` is inverted for `sessions.ts` and `community.ts`: every export needs `requireRegisteredUser(` or an entry in `GUEST_ALLOWED` / `OWNER_ONLY` with a reason. `results` sends `hasCoffee` only to owner/admin or for revealed samples.

### Group Sessions Pattern
- **`createSession`** (solo) uses `redirect()` inside — do not modify; it cannot return a value.
- **Group notice timing (S8-17, C8)**: a LIVE group session (no `closesAt`) emails its linked tasting group from `startSession`, not at creation; async sessions still notify at creation. `startSession` sends only when its own `updateMany` flipped the row; `notifyGroupOfSession` itself claims `groupNotifiedAt` atomically before sending (a direct call on an already-notified session is `invalid_input`; S8-28 D-09) and clears it when nothing went out (`keepNoticeStamp`; rate limit / error) — a failed notice never blocks the start, it returns `groupNotice` for a non-blocking owner notice. The choice persists as `CuppingSession.notifyGroupAtStart`; rules in `lib/groupNotify.ts`. **S10 C8:** the owner of a LIVE session may instead choose "at creation" (`notifyGroupWhen: "create"`): `shouldNotifyAtCreate` then sends from `createGroupSession` and `notifyAtStartFlag` stores false, so one choice never sends twice. A live session ticked "at start" that later gets a closing date (`updateSession` -> `planClosesAtChange` turns it async) notifies at that edit (`shouldNotifyOnBecomingAsync`, `groupNotice` reported non-blocking, `notifyGroupAtStart` cleared): exactly one of creation / start / that edit sends.
- **`createGroupSession`** is a separate action that returns `{ sessionId, inviteToken }` without redirecting, enabling the two-step wizard (Step 2 shows invite link).
- Invite tokens are `crypto.randomUUID()` stored in `SessionInvite`. `joinViaToken` is pure Prisma (postgres role, no admin client needed): the owner opening their own link and an existing participant re-opening it are no-ops (no `useCount` burn, owner never demoted to `joined`); a closed session sends members to `/results` and refuses newcomers with `session_closed`; `maxUses` is enforced inside the transaction (increment on the locked row, then check, throw to roll back) so simultaneous scans cannot overshoot the seat count.
- **Join rules (S8-11)**: the decision lives in the pure `evaluateJoin` (`lib/joinRules.ts`), used by BOTH `/join/[token]` (renders the state; a refused link never offers the anonymous sign-in) and `joinViaToken` (enforces it; non-group sessions are `invalid_input`). `SessionInvite.active=false` (set by "Regenerar enlace" via `regenerateSessionInvite` in `lib/invites.ts`, `import "server-only"`) reads as expired everywhere; `createInviteToken` is idempotent (`ActionResult`) and `getLatestInvite`/`resolveOrCreateSessionInvite` are the only invite lookups. `CuppingSession.entriesLocked` (owner `setEntriesLocked`) refuses NEWCOMERS with `entries_closed`; it is gating only, never read by scoring, the trigger or `AggregateScore`. The owner's "enviados" counter is `lib/submitProgress.ts` (cuppers with every sample submitted, never a `+1` per event). Group emails build session links with `groupSessionInviteUrl`.

### Realtime (Group Sessions)
- Use `createBrowserClient` from `@supabase/ssr` in client components.
- Subscribe to `evaluations` table updates **without a filter string** to avoid Realtime filter length limits. Filter client-side by comparing `payload.new.session_sample_id` against a `Set` of the current session's sample IDs.
- Requires `ALTER TABLE evaluations REPLICA IDENTITY FULL` (in rls_and_triggers.sql) so UPDATE events include full row data.
