# Auth and accounts

### Auth Pattern

- **Guest → account ("claim")**: QR walk-ups are anonymous Supabase users. The results-page banner (`components/results/GuestSaveCta.tsx`) does NOT run its own auth — `startGuestClaim` mints a signed claim token (`lib/guestClaim.ts`, HMAC, 7 days) and sends the guest through the normal login page with `next=/auth/claim?token=…`; after the magic-link/Google sign-in, `app/[locale]/auth/claim/page.tsx` shows a confirmation card (name + session count — **never merges on GET**) whose button runs the `confirmGuestClaim` server action → `mergeGuestData`, which moves EVERY user-referencing row from the anonymous id to the signed-in account (new or existing) inside one transaction and deletes the anonymous user. When you add a table with a user FK, add it to BOTH `mergeGuestData` AND `deleteAccount` (`lib/accountDeletion/deleteAccount.ts`) plus the manifest — the final `profile.delete` there fails loudly (rollback) if a Restrict FK was forgotten, but Cascade FKs would silently drop rows. **S8-07:** the token, `safeClaimBack` and `anonEvalWins` live in the pure `lib/guestClaimToken.ts` (tested); `confirmGuestClaim` returns an `ActionResult` (retry card on transient failure, `lookup_failed` ≠ `not_anonymous`); every user-referencing column — FK or bare (`AiChatUsage`, `OutboundEmailEvent.actorKey`, `CloseEmailDelivery`) — is listed in `lib/accountDeletion/manifest.ts`, and `tests/profileRelations.test.ts` fails on an unlisted `Profile` relation or a manifest table the merge does not touch.
- **Account deletion (S8-19, F-cuenta-1, E3 (a))**: `deleteAccount` (`app/actions/account.ts`, `run()`, `requireUser` — guests may delete themselves; typed `ELIMINAR`/`DELETE` re-checked on the server; super-admin refused with `account_protected`) → `lib/accountDeletion/deleteAccount.ts`. The pure `planAccountDeletion` (`lib/accountDeletion/plan.ts`, tested) decides: solo sessions and group sessions where nobody else evaluated are deleted through the `deleteSession` path; the rest are kept (live ones closed first via `closeSessionInternal`, reason `owner_deleted`, emails skipped). **S9-01 (A-07):** in sessions that are not closed where the person only PARTICIPATED and submitted nothing, the planner drops their participant row and draft evaluations (`dropParticipationSessionIds`, `isDroppableParticipation`) instead of reassigning them, so the placeholder cannot freeze the "everyone submitted" rule. One transaction (`{ maxWait: 15_000, timeout: 120_000 }`, the profile page exports `maxDuration = 300`) creates a placeholder profile PER deletion (`deleted_<random>`, never a shared tombstone — `Evaluation` is unique on sample + cupper), moves kept rows to it (evaluations WITHOUT touching `isDraft` so the trigger does not re-fire; participations WITH `excludedFromResults`), anonymizes coffees with `anonymizeOwnedCoffees` (shared with `deleteCoffees`), erases the rest per the manifest and ends with the uncaught `profile.delete`. The auth user is deleted after commit (3 attempts; orphan logged, runbook §24). Render placeholder names with `profileDisplayName` / `isDeletedProfileId` (`lib/accountDeletion/deletedProfile.ts`); anything that emails a participant must skip `isDeletedProfileId` ids; the Users directory hides them. It is a sanctioned post-close write too (full list under Session Lifecycle). It has never run against a database from a session: verify only on a throwaway account in a non-production environment.
- **Sign-out (S8-07)**: `signOut(locale, scope='local')` / `switchAccount(locale, next?)` return `ActionResult<{ next }>`; `SignOutButton` clears this device's caches only AFTER the server succeeded (offline → "Necesitas conexión"). Global scope exists only as the explicit "Salir en todos los dispositivos". A guest always gets the loss warning (copy rides on `GuestGateProvider.leave`). Email change is `requestEmailChange` (registered only, via `/auth/confirm`). `/join` runs `checkJoinable` (`app/actions/join.ts`) before `signInAnonymously`.

### Sign-in deep links, code entry and locale (2026-11, S8-06)
- **One `next` validator**: `safeNext(input, { origin?, fallback })` in `lib/safeNext.ts` (`safeNextPath` delegates). Never concatenate a `next` into a redirect without it. `safeClaimBack` stays (stricter).
- **Login CSRF guard (S9-02, A-08)**: every path that REQUESTS a sign-in link (`sendMagicLink`, `requestEmailChange` for both addresses) sets the httpOnly, SameSite=Lax, 1 h `cata_signin_intent` cookie with HMACs of the normalized address (`lib/signInIntent.ts` pure + tested, `lib/signInIntentCookie.ts` plumbing; never the address). `confirmEmailToken` verifies on an ephemeral client (`lib/supabase/ephemeral.ts`, no cookies, nothing persisted) and compares the cookie with the verified user's address. Match -> `setSession` on the cookie client (no extra step). No cookie or a different address -> NO session exists: the tokens are parked 10 min in the httpOnly, SameSite=Strict `cata_signin_pending` cookie (`lib/signInPending.ts` pure, `lib/signInPendingCookie.ts`, read/written/deleted only by `app/actions/auth.ts`) and `ConfirmClient` shows "Vas a entrar como <FULL address>" (a mask is defeated by a same-letter address). "Sí, continuar" = `acceptPendingSignIn(shownEmail, …)` (resolves the parked user with `getUser` and refuses with `conflict`, deleting the cookie, unless its address equals the one the card displayed; then `setSession`); a transient failure (`classifyPendingFailure`, `lib/signInPendingRules.ts`: network/5xx/unknown = retry) KEEPS the cookie and returns `unknown` so the same button retries, a definitive refusal (401/403, session/refresh token gone) deletes it and returns `token_expired`; a failed zero-click `setSession` parks the tokens too instead of throwing; "No soy yo" = `rejectPendingSignIn` (revokes only the parked session via `auth.admin.signOut(accessToken, "local")` on the ephemeral client, always deletes the cookie, never touches the browser's existing session). Both are callable unauthenticated by design. `verifyEmailCode` is exempt. Any NEW path that sends a sign-in link must call `rememberSignInIntent`.
- **A GET never consumes a one-time token.** `app/auth/callback` only redirects `token_hash` links to `/{locale}/auth/confirm`; the button runs `confirmEmailToken`. The 6-digit code goes through `verifyEmailCode`. Templates live in `docs/auth/email-templates/` (pasted manually, runbook §15).
- **Auth state**: `getAuthUser()` / `requireAppUser(locale, nextPath)` in `lib/auth.ts` over the pure `lib/authState.ts`. `none` redirects to login WITH `next` (proxy first, page backstops second); `unreachable` throws to the error boundary. Anonymous guests are `user`; `proxy.ts` keeps the guest branch first.
- **Auth errors**: `lib/authErrors.ts` is the one map to `auth.errors.*`; the shared sent state is `components/auth/EmailSentState.tsx` (login + founding-seat form).

### Guests (anonymous users)
- `proxy.ts` redirects `user.is_anonymous` away from anything under `/app` that is not `/app`, `/app/sessions`, `/app/sessions/[id]/(cup|waiting|results|print)`, or `/app/profile(/history)` (`lib/guestScope.ts`, unit-tested). Guests cup, see results and their own profile; they never create assets under a throwaway identity. The redirect lands on `/app/sessions?gate=1`.
- **Shared device ("¿Eres {nombre}?", S10 WP8, F-guest-4, `TODO(kim-validar:E1)`)**: `joinScreenFor` (`lib/joinRules.ts`, pure, tested) makes `/join/[token]` render `components/join/GuestIdentityChoice.tsx` instead of auto-redirecting/offering the join button when the viewer is ANONYMOUS and `evaluateJoin` says `redirect` or `ok`. "No soy {nombre}" confirms, then `signOut(locale, "local")` (called directly, not through `feedback.run`; failures show a toast) and only after it succeeded `announceIdentityLeft` + `clearLocalDeviceState()`, then a hard navigation to the same join URL; it re-checks `is_anonymous` with the browser client and never signs out a registered user. Nothing is deleted from the draft store (unsynced count comes from `countWarnable`). Every action on the screen (continue, join, "No soy", the draft sync) first classifies `getUser()` against the rendered id (`classifyGuestLookup`: a missing session counts as a different user and only refreshes; only network/5xx is an error). **Old tabs (third + fourth review)**: the five live cup-page writes (`upsertEvaluation`, `upsertPhysical`, `upsertExtrinsic`, `submitAllEvaluations`, `finishSoloSession`), `completeGuestOnboarding` and the three replay actions take an optional `expectedUserId` = the user the page was RENDERED for (`requireUserExpecting` in `lib/auth.ts`, built on `getAuthUser`; pure table `decideServerIdentity` in `lib/expectedUser.ts`). **"Identity changed" means ONE thing: a user IS signed in and it is a DIFFERENT user.** Only that throws `identity_changed` (before the profile upsert and before any read or write; live writes answer it as an `ActionResult` error, replays answer `pending`, draft kept, no attempt burnt). Nobody signed in, or an unreachable auth lookup (network, 5xx, 408, 429), is NOT an identity change: live writes behave as `requireUser()` does on main (`not_authenticated`, the client keeps the save pending and retries) and replays answer `pending`. Absent argument = `requireUser()` byte for byte. `CupClient` freezes its user id at mount, passes it on every write and latches ONLY on the server's `identity_changed` (`lib/identityResolve.ts` `onServerIdentityChanged`); any other failure is an ordinary pending save. The latch (`lib/identityChange.ts`) is module-level: it lasts until a reload or until a later check sees the SAME user signed in again (`clearIdentityChanged`), across client navigation. While latched the cup page sends no live writes (the draft stays local under the rendered user's key, nothing deleted; saves report `pending`, never green) and "Enviar" shows the `identity_changed` toast instead of doing nothing. The offline replay does not read the latch: the server-side `blob.userId` check protects it. **Where the notice shows**: on the cup page inside `OfflineBanner` (identity first, then the new-version notice; the cup shell is `fixed inset-0 z-40` and covers the app bar), on every other app page in `components/layout/IdentityWatcher.tsx`'s bar; `OfflineBanner` registers as the notice host so the two never show at once. `IdentityWatcher` reads who holds the cookie with `auth.getSession()` (a local read, no `/auth/v1/user` per resume; the server stays the authority for writes) and classifies it (`classifyBrowserSession`): on mount and foreground/bfcache resume `different` latches, `same` clears the latch, `none`/`unknown` do nothing (`actionOnResume`); on a `cata_identity_epoch` `localStorage` marker (written by "No soy" and `SignOutButton`; `storage` fires only in OTHER tabs) naming this tab's user (or nobody in particular) it re-reads, and `different`/`none` latch, `same`/`unknown` do nothing (`decideForMarker`, `actionOnMarkerRecheck`); a marker naming another user is ignored. **Guest finishes the claim in another tab**: if the completion marker (`cata_claim_done`) says the RENDERED anonymous id was claimed by the CURRENT user (`claimedRenderedUser`, `lib/offline/claimMarker.ts`) it is the same person: no notice; the cup page first awaits its pending draft writes (`registerBeforeIdentityReload`), then `rekeyUserBlobs(anon, account)` and a reload so the tab renders for the account. The claim markers are no longer cleared by the re-key (they expire by TTL, exactly `CLAIM_MARKER_TTL_MS` = 1 h from the DONE marker, pinned in `tests/claimMarker.test.ts`; `decideClaimRekey` reports `clear` for a stale one and `UnsyncedGuardProvider` removes both keys on read; every app mount re-runs the idempotent re-key), so edits written under the anonymous id later are still moved. **S10 leftovers C1/C2:** the ORDER of the two identity sequences is a pure, tested function (`lib/identitySequence.ts`: `sequenceIdentityReload` = before-reload hooks, THEN re-key, THEN reload, used by `reloadIdentity`; `sequenceLeaveAfterSignOut` = server `signOut` first, only then announce and clear the device, used by "No soy"), and after the cup page's own `awaitClaimRekey` moved drafts it kicks ONE `retrySync` (`shouldKickReplayAfterRekey`, `lib/offline/claimMarker.ts`, once per page through a ref) because the provider's re-key then finds nothing left to move and would never kick one. `classifyGuestLookup` (join screen only, unchanged) is built on `classifyIdentityLookup` (`lib/expectedUser.ts`): `AuthSessionMissingError` and any 4xx auth API error mean "no session"; only status 0, 5xx or a non-auth error is "unreachable". The screen's `pageshow` reloads a bfcache restore only after "No soy" (`leaving`). `GuestJoinForm` passes the id `signInAnonymously` returned (or the reused anonymous id) to `completeGuestOnboarding(name, expectedUserId)`; a mismatch writes nothing. The sync wait in the dialog is capped at 8 s, the dialog replays the guest's own drafts via `useOfflineSync().retrySync` before counting what is left, and a newcomer joins through `joinSessionAsGuest`. `GuestJoinForm` reuses silently only the anonymous id its own tab created (`sessionStorage`, 10 min, cleared on success or a final refusal; `existingUserAction`); any other anonymous user makes it refresh. No server action was added. **WP8b follow-ups**: (1) claim freshness is measured from the DONE marker (`decideClaimRekey`; a never-completed claim still expires from its start marker); both reload buttons call `reloadIdentity()` (`lib/identityResolve.ts`: before-reload hooks, re-key if the markers say so, reload) and the hook clears the cup page's pending refs/timers; the cup page awaits `awaitClaimRekey` (`lib/offline/claimRekey.ts`) BEFORE its first `loadSession`; `rekeyBlob` keeps the newer module per `updatedAt` (tie = the account's copy). (2) Sign-in completion writes `cata_identity_epoch` with `kind: "signedIn"` (`announceSignedIn`; Google via `rememberSignInStarted` + `announceSignedInIfStarted` on shell mount); a receiving tab that reads `same` clears its latch. (3) The latch toasts once. (4) `replayEvaluation/Physical/Extrinsic` answer `identity_changed` (distinct from `pending`) for a positively different signed-in user; `useOfflineSync` maps it to `waiting` and latches. (5) `joinSessionAsGuest(token, locale, expectedUserId)` -> `joinViaToken(..., expectedUserId)` refuses a different signed-in user. (6) `cup/error.tsx` shows the stale/identity notice in its failed state.
- **One nav, one profile page for everyone** (2026-09-26): guests see the same tabs and the same profile layout as registered users — limits live in access, not in shape. `app/[locale]/app/layout.tsx` wraps the shell in `GuestGateProvider` (`components/guest/`), which owns the "Termina de crear tu cuenta" `ResponsiveDialog` (opened by `?gate=1` too) and whose CTA runs the normal claim flow via `hooks/useGuestClaim.ts` (shared with `GuestSaveCta` and the profile's `GuestClaimButton`). **Every link from a guest-reachable page to a gated area** (Cafés, Grupos, Insights, `sessions/new`, `coffees/[id]`) MUST be a `GuestGateLink`, not a `next/link` — it renders the plain `<Link>` for registered users and a same-looking button that opens the modal for guests, using the same `isGuestAllowedPath` predicate as the proxy so client and server can never disagree. Copy lives under `guestGate` in `messages/*.json`.
