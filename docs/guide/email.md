# Email

### Auth Pattern

- **Outbound email is budgeted (S8-03)**: reserve BEFORE sending with `reserveEmailBudget` (`lib/emailBudget.ts`; numbers in `lib/emailLimits.ts`, ledger `outbound_email_events` keyed by HMACs from `lib/emailKeys.ts`, never a raw address or IP). Sign-in links go through `sendMagicLink` (`lib/magicLink.ts`, origin via `pickTrustedOrigin`); group mail goes through `deliverGroupMail` (`lib/groupEmail.ts`, per-recipient `group_email_deliveries` ledger, bounded retry, results labelled by name or `maskEmail`). A refusal is the typed code `rate_limited`; if the DB write already succeeded the action returns ok with `emailBlocked: "rate_limited"`. Logs carry ids and codes only, never an address or a provider response body. Signed-in requesters also reserve a per-account `magic_link_user` bucket (`MAGIC_LINK_PER_USER`, S8-28 A-04), and the daily close-expired-sessions cron purges ledger rows older than the longest window (`purgeEmailLedger`, A-03). **Reservations are atomic per bucket (S9-04)**: `reserveEmailBudget` runs each reservation in ONE `prisma.$transaction` that first takes `pg_advisory_xact_lock(hashtextextended(key, 0))` for every bucket it counts against, in sorted key order (no deadlocks), then counts and inserts on `tx`; exactly `limit` of N simultaneous requests pass (tested in `tests/db/emailLedgers.dbtest.ts`). Transaction-level locks only (pooler-safe); a lock wait over 4 s or a transaction over 10 s THROWS (callers see `unknown`, never an allow), and callers must not call it from inside another interactive transaction. Runbook §11, SQL PHASE 22.
- **Per-group unsubscribe (S8-20)**: `deliverGroupMail` appends the footer link and the RFC 8058 `List-Unsubscribe` headers to every group mail (token = group id + HMAC of the member row's STORED address, `lib/groupUnsubscribe.ts`, own domain prefix, no expiry; link origin `siteOrigin()`), and the plan step drops members with `emailOptOutAt` set BEFORE the budget (ledgered `skipped`/`opted_out`, never retried, not counted). Public route `app/api/groups/unsubscribe` (GET confirm, POST opt-out/one-click; every failure is the same neutral 400). Only the member clears it (`setGroupEmailOptOut`); never reset `emailOptOutAt` from an owner action. New `GroupMailJob`s must pass `memberEmail` (stored) and `locale`. Runbook §25.

### Session Lifecycle (see docs/flows.md for diagrams)

- **Close emails are ledgered**: `close_email_deliveries` (one row per session × participant, status `sent | skipped | failed`) makes `sendCloseEmails` skip already-sent recipients; `resendCloseEmails` (owner) retries the rest. **Reserved before sending (S9-01, B-08):** each recipient is claimed as status `sending` (`create`, else one conditional `updateMany` over `failed | skipped | sending` older than the lease) BEFORE the PDF render and send, so the cron repair racing an owner resend cannot double-send; a `sending` row older than `CLOSE_EMAIL_LEASE_MS` (10 min, crash recovery) is claimable again (so a fresh `sending` row blocks a resend for that recipient until it is 10 minutes old, and a resend with nothing claimable returns `nothingToSend` without spending budget); the final status write only lands while the row is still `sending` (a real `sent` always lands); rules in the pure `lib/closeEmailLedger.ts`; the results line counts `sending` as pending. **Resend is bounded (S9-01, A-09):** `resendCloseEmails` reserves a `close_resend` ledger event per session (`CLOSE_RESEND_PER_SESSION`, 3 per hour, `lib/emailLimits.ts`, no migration) and returns `{ ok: false, error: "rate_limited" }` when spent. Anonymous guests have no email → `skipped`, not `failed`. Fan-out is bounded (4 concurrent PDF renders). Pages that invoke these actions export `maxDuration = 120`.

## Styling

- **Newsletter sign-up (2026-11-15)**: the closing block's `NewsletterForm` posts to `subscribeNewsletter` (`app/actions/waitlist.ts`): honeypot, address check, a per-address and per-IP limit through the ledger's `code_verify` kind with the subject prefix `newsletter:`, then ONE write. It sends no email and creates no account. **There is no newsletter table** (a migration is the owner's): a subscription is a `waitlist_entries` row, rules in the pure `lib/newsletter.ts` (`tests/newsletter.test.ts`): a new address gets `plan = "newsletter"`, `source = "newsletter[:tag]"`, `consentAt`, `consentNoticeVersion = NEWSLETTER_NOTICE_VERSION`; an address with a founding row keeps it and gets the dated mark `+newsletter@YYYY-MM-DD` at the end of `source`; `reserveFoundingSeat` turns a newsletter-only row into a reservation dated that day (`foundingUpgrade`); `planWaitlistMerge` lets a reservation beat a newsletter-only row whatever their dates and carries the mark (never the newsletter's consent stamp onto a reservation). Retention is the reservations' own (orphan rows purged at `WAITLIST_RETENTION_MONTHS`). Anything that counts founders must filter `plan <> 'newsletter'`. The privacy policy states it (sections 2.1, 3, 10, 11; text version 1.1; `CONSENT_NOTICE_VERSION` `2026-11-v2`); manual unsubscribe and the owner's open decisions (confirmed addresses, a real table, an unsubscribe link) are runbook §37.
