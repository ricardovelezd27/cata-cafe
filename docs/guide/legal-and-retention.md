# Legal and retention

Legal pages (S10 WP9a): three public static pages, `/privacidad`, `/terminos`, `/aviso-legal`, rendered by `components/legal/LegalPage.tsx` from typed docs (`LegalDoc` in `lib/legal/types.ts`: `title`, `version`, optional `intro`, `sections` of `heading` + blocks; a block is a string paragraph, `{ sub }` (an h3), `{ list }` or `{ rows }` two-column table). The Spanish text (`lib/legal/es/*`, adapted from the owner's documents, `// ADDED`/`// ADAPTED` mark what is not in the source) is the original; `lib/legal/en/*` is a block-for-block translation whose intro starts with "the Spanish version prevails" (`tests/legalDocs.test.ts` keeps the structures equal and bans placeholders). Company facts live in `lib/legal/company.ts`. `lib/legal/config.ts` `LEGAL_PAGES_PUBLISHED` (`true` since 2026-11-13: the owner read the pages and said "Yes, publish"; with the Registro Mercantil line still missing by his explicit decision, recorded as `REGISTRY_PENDING_BY_OWNER` in `lib/legal/company.ts`: set it to false in the change that fills `LEGAL_ENTITY.registry`, `tests/legalDocs.test.ts` requires it) gates every link/notice (footer, login line, waitlist notice, consent stamp), the "Borrador" banner and `noindex`; **because the pages now PROMISE the 12-month deletion of never-used accounts, `UNUSED_ACCOUNT_PURGE_ENABLED=1` must be on, after the runbook §17 item 4 rehearsal, before 2027-05-30 (the oldest never-used account's 12 months, read from production on 2026-11-13: 30 never-used accounts, none due)**; `CONSENT_NOTICE_VERSION` is `2026-11-v1`. Open `TODO(owner)` items: Registro Mercantil (`LEGAL_ENTITY.registry`), founding-offer conditions, Vercel/Resend transfer safeguards, contact address. The daily close-expired-sessions cron also runs `purgeUnusedAccounts` (`lib/unusedAccountPurge.ts`, server-only; owner decision 2026-11-14: accounts that were NEVER USED are really deleted with their reservation after `WAITLIST_RETENTION_MONTHS`). Every reservation or sign-in request creates an auth user and a profile at once, so the rule is on the AUTH row: pure `notUnusedReason` (`lib/unusedAccountRules.ts`: not anonymous, has an email, never confirmed / never signed in, not invited/SSO/banned/soft-deleted, not the super-admin or an AI admin, the LATEST of `created_at`, the four access-email columns (`GREATEST`) and the newest reservation at the same address strictly before `waitlistPurgeCutoff`, no access email in the last 48 h) mirrored in SQL against `auth.users` (candidates selected in SQL, oldest first, 50 per run; `tests/db/unusedAccountPurge.dbtest.ts` proves the two agree). The account must also be EMPTY: `UNUSED_ACCOUNT_RULES` has one rule per `PROFILE_MANIFEST` entry (`blocks` = shows use, never deleted, counted `skippedUsed`; `erase` = own bookkeeping or a grant TO it; `unlink` = a group owner's roster row keeps the typed address and loses the link) and `tests/unusedAccountRules.test.ts` keeps its keys equal to the manifest, so a new user-column table fails the build until ruled on; an unknown key blocks. It does NOT reuse `deleteAccountData` (that always creates a `deleted_<random>` placeholder and re-plans sessions/groups): one short transaction per account (re-check, unlink/erase, `profile.deleteMany` last), THEN the auth user through the exported `deleteAuthUser` (3 attempts, orphan logged; database-first so a failed admin call leaves an auth user the next run retries). Reservations with no auth user at all older than the cutoff go too (500 per run). **Switch: `UNUSED_ACCOUNT_PURGE_ENABLED=1`** (`isUnusedAccountPurgeEnabled`, `lib/features.ts`); OFF (default) = count only plus one `unusedAccount.switchOff` warning; the cron JSON carries `unusedAccounts: { due, deleted, skippedUsed, failed, enabled, orphanReservations }`. Runbook §17 item 4 has the read-only counts, the rehearsal and the deadline (switch on before the oldest never-used account turns 12 months). Email change (H1 third review, M-a fifth round): `requestEmailChange` records `{ from, to }` ONLY in `app_metadata.email_change` through the service role, AFTER `updateUser({ email })` succeeded (`recordEmailChange`, `lib/emailChangeMove.ts`; `from` = the address the server read for the signed-in user, `to` = the address the server passed to `updateUser`; each request overwrites the record; the admin write sends ONLY that key; `user_metadata` is user-writable and is NEVER read for this). `moveReservationAfterEmailChange` (same file; `completedEmailChange` in `lib/emailChangeRules.ts`: no pending `new_email` AND the verified account's current address equals the recorded `to`, else the record is inert) has ONE call site, `confirmEmailToken` right after `verifyOtp` succeeded for `type=email_change`, BEFORE any session handling, so it runs whether the person is signed in zero-click, parked, accepts, rejects ("No soy yo") or never answers (GoTrue has completed the change either way; `acceptPendingSignIn`/`rejectPendingSignIn` never move anything; `tests/emailChangeRules.test.ts` pins the order). It refuses (and keeps the record, logging `old_address_held`) when ANOTHER auth user holds the old address, moves the `WaitlistEntry` row with `moveWaitlistEntry` (`lib/waitlistMove.ts`) so a used account keeps its reservation, and clears the record (only its key). The orphan-reservation path has NO exception for email changes (while a change is in flight the account still holds the old address; a stale record protects nothing). Addresses compare as `lower(btrim())` in SQL and `normalizeAddress` (`lib/emailChangeRules.ts`) in code: lowercase, SPACES trimmed only, never widened; the job re-checks the auth row once more right before `deleteAuthUser` (`unusedAccount.signedInDuringPurge`); changes completed before the deploy cannot be reconciled. **Reconcile + merge (S10 leftovers A1/A2):** a move that failed at verify time is retried by the daily cron's `reconcileEmailChanges` (`lib/emailChangeReconcile.ts`, runs BEFORE the unused-account pass, whether or not the purge switch is on, deletes nothing): it selects in SQL up to 50 accounts whose `raw_app_meta_data.email_change` is an object, not soft-deleted and with NO pending change (`coalesce(u.email_change, '') = ''`; GoTrue keeps the pending address there, such accounts would answer `keep` forever), in `order by random()` (so the few records kept for good, `old_address_held` or an ambiguous reservation, cannot block the head of the batch), reads each through the admin API and applies the pure `reconcileAction` (`lib/emailChangeRules.ts`): `move` only when `completedEmailChange` agrees (it calls `applyEmailChangeMove`, the SAME function `moveReservationAfterEmailChange` wraps, so the refusals are identical: `old_address_held` keeps the record), `clear` for an inert record (nothing pending and the account's address is not the recorded `to`; only that key, and only after RE-READING the user and finding the record unchanged, `sameEmailChangeRecord`, else `kept`), `keep` otherwise. The pass respects the route's start budget (`mayStart`): skipped when spent (`emailChangeReconcileSkipped: true`) and it stops between accounts (`budgetTruncated`). **Cron status (`cronStatus`, `lib/cronPass.ts`):** a failed deadline-close or repair pass makes the run RED (HTTP 500, `ok: false`) but the later passes still ran and the full JSON is returned; reminders, idle and reconcile failures keep 200 with their flag. `runPass` logs `code`, else `errorCode`, else the constructor name, never the message. Cron JSON `emailChangeReconcile: { seen, moved, cleared, kept, failed }`. When the NEW address already has a reservation, `moveWaitlistEntry` MERGES in one transaction (`planWaitlistMerge`, `lib/waitlistMoveRules.ts`; result `merged`): the EARLIER-created row is kept at the new address with its own source/locale, takes the other row's consent stamp (the pair) only where its own `consentAt` is null, the other is deleted; more than one row at either address changes nothing (`target_exists`). `normalizeEmail` (`lib/accountDeletion/plan.ts`, JS `trim()`) and `normalizeAddress` stay SEPARATE on purpose (SQL `btrim()` trims spaces only; pinned in `tests/reconcileAction.test.ts`). `listAllAuthUsersStrict` throws `auth_list_truncated` at its page cap. `i18n/routing.ts` sets `localeCookie: false`: the app never read `NEXT_LOCALE` (detection is off), so next-intl no longer sets it and the cookie table in the privacy policy does not list it; when the flag is true the three pages are also in `app/sitemap.ts`; `WaitlistEntry.source` is stamped by `reserveFoundingSeat` (`lib/waitlistSource.ts`); `consentAt/consentNoticeVersion` are null until `LEGAL_PAGES_PUBLISHED` is true (`consentStamp` in `lib/legal/consent.ts`) because no notice is shown before that.
